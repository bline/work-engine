## Open / residual risks
1. `parse_json` replaces non-integral literals that `f64` would collapse by `0.5` and over-wide integrals by `±1e40` inside the validated `Value`. This is exact for every published numeric domain (only integer-typed locations are numerically constrained, no `number` type or numeric `const/enum` exists) and for the unconstrained wire `derivations` items; a future schema that constrains non-integer numbers or uses numeric `uniqueItems` on huge literals would need the exact value carried (the Rust diagnostic for such a rejected fraction prints `0.5`, not the original literal).
2. The public `Value` API (`validate_accounting_bundle`, `validate_schema`) cannot see literal text a stock-`serde_json` caller already collapsed; it is controlled but face-value (documented, tested).
3. The panic audit is a seeded sample (1308 runs), not exhaustive; Python `jsonschema` is a second oracle only where Python's float parse is exact.
4. Python `re` `$` accepts a trailing newline that ECMA/Rust reject — affects Python reference checks only (`schema_agreement.py`, `wire_corpus.py` do not probe it).
5. Recompilation of `ck.schema.json` is required (compiled in): any consumer pinning the old schema bytes (acknowledgements are all null) sees new digests for the 18 nodes/consumers above.
6. Independent Fable review of this exact diff is outstanding by design; oracle-owned files were not touched. `cargo test` lib suite takes ~95 s in debug.
