Yes. **Make admission a one-shot commitment, not permission that can be silently revoked while the operation is acting on it.** That directly addresses the revocation race the review found.

The point of no return would be **before the Server’s first write**. At that point, the system checks that the exact Campaign head, operator approval, and Builder job still match, then consumes the approval for that one attempt. If revocation wins before that point, the attempt refuses without writing. If admission wins, changing the approval afterward does not invalidate the running attempt. To stop it early, you terminate the execution. That’s an **abort with possible effects**, not a clean refusal: files may already exist, Host may already have started, and the system must record what happened or mark the outcome unknown.

Two details matter:

- **The lock must cover the actual execution.** Today Server hands off to a detached collector, which can start a separate Host process. Killing the request handler or even Server is not proof that Host and its runtime stopped. The system should not release the execution lock or admit a replacement until it verifies that the covered execution has stopped. Normal completion retires the approval; it never makes it reusable.
- **Locking approval doesn’t lock the Campaign head.** If the requirement is still that the head remain current through actual Host entry, the Campaign owner must also prevent conflicting advancement during that interval. Alternatively, you could explicitly decide that the exact head committed at admission remains authoritative for that attempt even if the Campaign later advances. Those are different contracts.

I’d favor the one-shot commitment. It makes the consequence explicit: **before admission, revoke; after admission, abort and reconcile.** It resolves the revocation question, but not the early task read. The commitment should cover only the approved preparation and entry; it should not authorize opening or delivering the protected task.
