**Architecture verdict: retain H1–H5 and the Host/fixture/RL ownership split; require a local amendment to the qualification contract.** The Host must establish that it completed the required cleanup action, not merely that every process in its log was clean. The fixture must establish what it received, which child exited, and which Engine answered its independent query. Neither owner can supply the other’s evidence.

### What clean cancellation must establish

RL `043-u4a-held-contract.md:11,17–25` assigns the Host the child and exact stop. The accepted cancel concludes after bounded exit collection and exact removal observed against the owned identity. `review-r2/PLAN.md:15–17,24–27` separately requires an independent post-exit observation of absence. These requirements answer different questions: **did this Host complete the cancel it accepted**, and **was that original container absent afterwards**? An observer finding an empty daemon result answers only the second. RL `041:13–17` already distinguishes physical cleanup from clean held cancellation in the earlier EOF probe.

For this realization, **yes, an affirmative Host-attributed normal removal is required.** The selected launch is `create` without automatic removal (`pi_coding.rs:666–713,924–950`); the Host’s normal terminal path inspects the exited container, waits, removes the original ID and queries its disposition (`pi_host_held.rs:1532–1570`). If another actor removes it after `wait` while the Host cannot even start its removal, a positive result would qualify a Host whose cleanup did not work. The failure has a consequence independent of violating a code convention. An additional empty query cannot fix it.

This does **not** make a particular CLI spelling, stdout format, or independent forensic proof of the sole physical remover an RL contract. On the trusted pinned CLI/Engine route, require an attributable normal operation against the original full ID and launch Engine, with an affirmative result under that operation’s actual semantics, followed by the separate presence check. If a purported acknowledgement could equally mean “already missing,” it cannot by itself establish this distinction. A different Host-owned removal mechanism with equivalent evidence could satisfy the owner contract; it is not needed for this correction. Narrowing success to eventual absence regardless of how it happened would require an owner decision, not a test change.

### P0 — The set of recorded helpers is not the set of required actions

`OwnedContainer::start` allocates a sequence **before** executable verification, capture creation and spawn. Each can return before `command` appends evidence (`pi_host_held.rs:1284–1314,1371–1382`). `cleanup` folds that error into “normal `rm` not successful”; an absent result skips forced removal, and final absence yields `ConfirmedAbsent`. `Held::terminal` then asks whether **all existing command records** are clean, not whether a successful normal removal exists (`:841–856,1557–1570`). With a clean wait, two good empty answers and no spawned removal helper, the predicate can pass.

This is an **inherited start-error path**, not a regression in process-group enumeration: the same early return and removal branch exist in the sealed R1 patch at `validation/candidate.patch:1603–1627,1791` and R2 at `remediation-r2/candidate.patch:1583–1607,1806`. The correction now handles the previous *spawned* `rm` and final-query uncertainties. Its tests explicitly start `rm` and assert its invocation (`pi_host_held_tests.rs:193–217,470–547`). They do not establish coverage of a required command that never started. The recurrence is the loss of required evidence before the verdict, not a claim that an actual helper or container survived.

**Placement alternatives:**

| Alternative | Judgment |
|---|---|
| Add one affirmative `normal_removal` result to cleanup | **Necessary distinction and sufficient to close this particular false positive**, if only a successful normal exact-ID action can produce it. A boolean derived from absence, or a search for any command named `rm` including forced recovery, does not qualify. In isolation it still permits failed starts to disappear from diagnostics and does not solve the custody finding. |
| Make the held Host’s private action result total, and use the named removal result in the verdict | **Recommended.** At the existing `start`/`command` seam, give every attempted action a bounded result even when no process was obtained. Carry the selected operation/role, sequence and bound subject; distinguish setup failure/no child, spawned child with exit/group/intervention evidence, and the command-specific effect or observation. Keep record-persistence outcomes separate. `cleanup` returns both the normal-removal result and container disposition to the single terminal decision. A total log still cannot prove an action the caller omitted: the clean path must positively consume the named result. |
| Replace the CLI with a new Engine backend; make an external controller or RL own cleanup; add a general durable action service | **Do not reopen these boundaries.** A new backend still needs attribution and publication evidence and changes the execution subject. An external cleaner could make the final query pass while hiding a failed Host, and would acquire destructive authority the observer does not have. There is no demonstrated need for a second state machine, public action schema, or transaction log for every command. |

Require only the actions appropriate to the actual path. A pre-create refusal need not invent a removal, group, or ID. A known pre-spawn failure is **not** an unknown spawned group. A create that may have reached the Engine without attributable identity is **not** proof of non-creation. Keep the corrected distinction between a trusted create ID, a candidate usable only for bounded exact-ID corroboration, and unknown ownership (`pi_host_held.rs:1229–1281`). Unqualified process evidence must not discard a valid cleanup coordinate. Nor does retaining that coordinate authorize touching a replacement. After the last helper, a clean Host verdict needs the existing ready/cancel/close, through-exit attempt and exit witnesses, the affirmative normal removal, clean evidence for the owned processes, no fallback intervention, and confirmed exact-ID absence. A failed verdict can truthfully carry `confirmed_absent`.

### P1 — Durable evidence and publication have different boundaries

The Host installs the attributable ID in memory before rewriting the owner file; ordinary error unwinding still reaches exact cleanup (`pi_host_held.rs:150–174,1238–1262`). That is worth retaining. But the earlier owner record can still contain a null ID. `finish` deletes command captures, including the create result, before the private evidence write; failure of that write is discarded if another failure already exists (`:827–838,1573–1591`).

The minimum correction is to preserve a **safe recovery coordinate**—run/job, bound Engine, original ID and its attribution—until a replacement is known persisted. Do not delete the last usable coordinate merely because it was copied into memory. Do not retain or expose raw inspect output, environment or arguments as a substitute. If the owner write fails, continue bounded exact cleanup from memory, report the primary **and** persistence failures on any surviving channel, and do not qualify. A null-ID intent is evidence of intent, not removal authority. If the private record is missing, there is no sealed private proof; if the terminal is missing, there is no published terminal success.

There is an unavoidable interval between an Engine effect and the Host receiving and durably recording its result. A crash there, or failure of all storage and reporting channels, can leave only intent or no usable evidence. The truthful result for the collector is **durable ownership/cleanup unestablished**, not “not created,” “recovered,” or “removed.” This amendment does not promise cleanup after Host death, atomicity across Docker and disk, a restart scanner, or a new recovery grant. Any such requirement needs a separate owner, authority and design.

**The terminal file is not the H4 publication boundary.** `lib.rs:116–136` renames before directory sync; a reported write error can leave the proposed positive bytes visible. `pi_host_held.rs:183–193` then marks the returned record failed on persistence error, or adds `publication_error` if the cancel reply fails. `bin/work-engine-pi-host.rs:69–86` exits successfully only for `held_cancelled` without a publication error. Conversely, flushing a reply is not the fixture observing a complete matching frame (`pi_host_serve.rs:79–90`). Do not attempt to make file, pipe and process exit one transaction. Keep one Host qualification decision; for **joined acceptance**, require the actually received matching reply, matching persisted terminal and bound private evidence, observed successful exit of that exact child, then the independent exact-ID result and retained run manifest. A candidate-positive file alongside a failed reply, nonzero or unobserved exit, or missing manifest is not a consumable H4 success.

### Bounded next scope and falsification gates

**First:** dev-vertical records its disposition against the exact history and freezes the amended acceptance rule. If adopted, two offline units can proceed independently: one writer for the private held Host action/cleanup/finalization seam and its tests; one writer outside the source tree for the fixture caller, independent reader and scripted peers. Agree the private join coordinates first. No edits to ordinary `serve`, profile policy, installed startup, shared protocol or RL are needed.

Use the following paired controls **through the actual owning callers**, not just fabricated terminal JSON:

1. **Same clean close, wait and final absence; different removal history.** A stateful scripted peer acknowledges normal removal of the original ID in the positive. In the negative, fault just `rm` setup (pin check, capture setup or spawn), let the ID independently disappear and let both absence queries succeed. Require `held_failed + confirmed_absent`, the failed attempted normal action with no child, and no force/name substitution. Also omit the required result entirely: even a clean remaining ledger must not qualify. Retain spawned nonzero/unknown-group/intervention cases, a failed last query versus exact present, and forced recovery that removes the right ID but cannot qualify.
2. **Same trusted create, different persistence.** Succeed normally, then fail the post-create owner write, private write, and both together, including a cleanup failure. Verify in-memory exact targeting and either a retained safe coordinate or explicit lack of durable custody. Remove/interrupt at intent-only, after create but before durable ID, after terminal rename but before directory sync, and after successful file write but before complete reply. Assert the distinction between surviving artifacts and consumable success. Missing or divergent file/reply, nonzero exit and no actual exit must each prevent a positive join.
3. **Same plausible caller transcript, different admission or bytes.** A matching initialize may send start; vary each available expected pin independently and assert **zero start requests**. Use a genuine Host-ready digest versus an identically repeated but wrong digest; the latter sends no cancel and cannot pass the retained join. Supply the matching private sidecar versus missing, swapped-run, altered-after-seal and mismatched-ID copies; no positive package for the latter cases.
4. **Same bad early controller reply, different actual child behavior.** Run the real outer caller against an owned scripted child that exits on EOF, then one that outlasts an injected short bound. The first records and reaps the failed child. The second records pending/authorized intervention and demonstrates actual custody transfer or collection. Neither publishes a positive witness. The existing test reaps its *own* cooperative subprocess outside the real outer failure path (`test_held_fixture.py:345–359`).
5. **Same `[]`, different query history.** Matched launch peer/Engine, exact full ID and bounded framed response with finality establishes absence; a row for that ID establishes present. Vary independently: changed Engine/peer/start; truncated length/chunk; extra data delivered together **or after** the body boundary; an extra response between `/info` and the material response; no finality before deadline. None can turn uncertainty into absence. Exercise pre-create image/name/label observations as well as post-exit original-ID lookup. Do not run these against Docker in this correction scope.
