## U4-A: establish held readiness offline (first slice)

**Protected consequence:** a trusted startup owner can tell whether the exact installed Pi realization has reached a state from which it could be activated, without that observation itself permitting provider entry or a task effect. If a fact required for activation cannot be observed or enforced, keep the hold and record precisely what remains unestablished.

- **Trust and scope.** Framed container–Host stdio is the declared crossing; the first candidate is a pinned, fresh-start, three-tool analysis profile (snapshot read, question open, result publish; no shell). Docker observations may establish named properties of the actual container inside the trusted Host/daemon boundary: mount set and access modes, network none, selected image/runtime/receiver, process limits and containment of descendants. They do not independently attest the daemon/kernel, continuous liveness, host FD enumeration, or Host behavior outside the container. Repository/task/installation state and provider credentials are not container mount inputs. Separately name every allowed mount, the allowed IPC observations/operations, and any fact requiring an observer independent of the Host. Keep the Host’s provider transport crossing separate.
- **Read the actual seam before choosing placement.** Current `run_pi_host` refuses with an installed hold; `native_startup.rs::publish` and task-host `AuthorizedResearchStartup::admit` consume Codex-specific observation/protocol evidence. Reuse the lifecycle of hold → observed readiness → one-use activation → lifetime cancellation where it fits; do not manufacture Codex evidence for Pi or generalize a boundary merely to share code. Trace whether Pi `thread/start` can reach provider or tool callbacks before the Host has reported a verified tool set. Compare an explicitly held Host startup with a pre-activation path using an existing demonstrably effect-free handshake. If neither can establish readiness without effects, record the need for an explicit Host gate before proceeding. Initial source trace: `pi-host/initialize` reports identity before container startup; `thread/start` verifies the requested tool list and enters Host startup; `pi-host/observe` happens after the startup reply and before the runner starts a turn. Controller provider dispatch requires an active turn. This is a useful candidate boundary, not yet proof that all startup paths are effect-free or that requested and effective tools match.
- **Evidence and custody.** Bind the proposed readiness observation to selection/config and installation, host and executable identities, protocol, composition and job digest, container ID and inspected profile, and the effective tool proof. Keep expected policy, Docker-observed facts, pinned/runtime-checked facts and Host protocol statements distinguishable. Check currentness before any activation; missing, stale, mismatched or unavailable evidence cannot release the gate. Publish only a held-readiness receipt at this stage, with a scoped claim and a terminal outcome on refusal. A receipt is neither activation nor research-result publication.
- **Offline proof.** A pinned controlled fixture should reach held readiness without transport entry or task effect. Negative cases: wrong container/job/pins; forbidden mount/network; early provider/tool intent; missing evidence; cancellation before release; attempted reuse/stale activation; and failure to observe cleanup. Verify no leftover child/container, or retain a named cleanup-unknown outcome. Production remains held throughout this first slice. Step 4’s already-active selected loopback run is regression evidence, not this held-start proof.
- **Owner checkpoints.** RL owns task-host and lifecycle admission/receipt semantics; dev-vertical owns the actual Pi Host controller and rendered container boundary. Resolve who observes what and the currentness interval with the protection owner before asserting production readiness. Any change to the shared Host protocol needs cross-owner coordination and new pin/evidence treatment.
