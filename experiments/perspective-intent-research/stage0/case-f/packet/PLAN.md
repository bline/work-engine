# Pi Host U4-A: offline held-readiness acceptance plan

Status: revised in response to the independent Astra review (board #6085; `review-r1/ASTRA-REVIEW.md`). RL cross-checked the prior version (board #6077). This revision has not been re-reviewed and is not a qualification result or implementation authorization. Based on `d410c9e1108d18e262fe60fcbe7a79b458e842a0`, RL `041-u4-protection-qualification-PLAN.md` and `043-u4a-held-contract.md`, board #6069 and #6071–6072. The latter documents own the broader qualification contract; this packet makes the checks observable. The #6069 pre-turn probe is a baseline, not a pass: an ordinary Host could still accept `turn/start` and EOF was not clean held cancellation.

## Claim and exclusions

A pinned selected Pi analysis realization can reach a verified receiver-ready state and be cleanly cancelled **without this construction loading credentials or attaching usable provider transport or a task relay/lease**. This does not assert the absence of ambient Host privileges. Qualification is for the exact tested candidate and observation, not installed startup admission, production protection, independent daemon/kernel attestation, activation readiness, continuing liveness, or authorization. The held arm has no activation operation. Preserve ordinary `serve`/EOF behavior, the startup hold, and the 8 MiB cap. No live calls, credentials, paid inference, provider/task relay bindings, or promotion of prior evidence.

## Independent checks and actual dependencies

| Check | Owner and route | Pass criterion / retained evidence |
|---|---|---|
| H1 — Capability construction | Host owner; source boundary plus targeted executable tripwires | Held selection precedes controller servicing and any credential read, transport construction or task relay/lease attachment. Same receiver registration inputs and provider/model *description* as the selected profile; no usable credential/transport/lease. Test with failing tripwires at actual construction/load boundaries; do not infer absence from no successful calls or unset env alone. Use an explicit, separate qualification entrypoint or launch variant, available only in `controlled-proof`; ordinary `serve`, installed selection and non-proof builds refuse the selector. Controller input cannot select or change mode. |
| H2 — Fail-closed controller/receiver handling | Host owner; independent injected-frame/state tests | Before ready **and** while held: matching `turn/start`, provider intent, and task/tool intent cannot enter effects; no generic start or activation command escapes. Exercise applicable early intents at their actual handlers, not only controller RPC. An unexpected effect intent invalidates qualification even when blocked; retain observed/refused/entered counts separately. Inject a provider attempt refused locally by the receiver that emits no Host request: receiver evidence must prevent a clean pass despite zero Host requests. Reject wrong pin/profile/session, active or duplicate ready, and wrong/additional/missing tool name. Show that no false ready or terminal success is produced. |
| H3 — Ownership and cleanup handling | Host owner; independently injected failure tests once cancel boundary exists | Wrong-session, premature or repeated cancel creates no new teardown authority; failure termination may still clean up under the Host's existing ownership. Include cancel after receiver `ready` but before verified inspection/publication, and accepted cancel followed by failed close delivery even when physical cleanup succeeds. Neither qualifies as `held_cancelled`. Through the actual held event loop with an open, silent controller after ready, separately exercise unsolicited receiver intent, receiver loss, and deadline expiry with both peers silent. Each must terminate as a bounded failure with a cleanup disposition without a later controller cancel or EOF; scripted peers suffice. EOF/malformed input, receiver failure, timeouts and failed/missing cleanup observation remain refusal/failure, never `held_cancelled`. Distinguish confirmed removal, removal failure and unknown cleanup. Preserve ordinary EOF/error diagnostics. |
| H4 — Joined positive witness | Host owner; requires pinned candidate + relevant container lane availability | Real selected receiver + real pinned Docker/Host. Start clean with no usable provider transport or task relay. Initialize → thread/start → validated same-session idle `ready` → fresh containment inspection and publication of the qualified ready record → explicit cancel bound to that record → delivery and consumption of that cancel's same-session `bridge_close` → matching receiver completion and successful bounded receiver/attach exits without fallback stop/kill → successful independent post-exit query confirming the original full container ID absent on the trusted launch daemon. The pinned receiver's correlated completion may establish consumption; EOF/failure closure cannot substitute for the accepted cancel. Reconcile receiver and Host observations through exit; show no forbidden attempt or entered turn, provider dispatch, tool or snapshot action, and no owned leftover child/container. Negative cases test unexpected intents separately. A missing observation is not a pass. |
| H5 — Containment/identity negatives | Host owner; bounded verifier negatives, with real Docker only where necessary to establish observation behavior | Mismatched container identity, job/pin, prohibited mount or network, and missing/failed fresh inspection never yield a valid held-ready record. Verify the rejected condition against the inspected/expected distinction; a mock-verified positive is not H4. Test stale/reassigned container name with a scripted Docker responder: no observation or destructive action on the replacement can stand in for the original. Test daemon mismatch or unknown identity as unqualified, not confirmed absence. |
| R1 — Consumer review | Research Lifecycle; after exact Host subject and witness are available | Cross-check binding, negative claims, and cleanup result against retained evidence. No task-host installed receipt adapter, activation permit consumer, or schema reuse with Codex in this slice. Scope any remaining protection/currentness owner questions as unestablished. |

Before H4, agree which ready and terminal fields the consumer needs and pin the candidate, rendered job and selected tool surface. H1/H2/H3/H5 can be exercised as their seams are ready; none requires the H4 outcome. The shared Cargo target and exact fixture container/state ownership are resource constraints, not semantic dependencies. RL U3-A redacted-head verification can proceed independently; do not edit its lifecycle-service path as part of this packet.

## Evidence acceptance

- Bind the witness to the candidate revision/diff, installed-equivalent selection/config, Host executable and protocol, composition and job, pinned runtime and receiver, same-process/session correlation and exact container ID. Name anything not actually tested through installed admission as such. Keep evidence for the actual validated receiver tool list (snapshot read, question open, result publish; no shell), not the requested list copied from config. It does not prove tool implementations or provider-wire tool tables.
- For the fresh inspection, retain safe measured fields (container identity, checked image, running state, user, network, read-only root, expected mount destinations and modes including no credential/repository/task mount), inspection digest and time. For limits, labels and capabilities, distinguish explicitly projected observations from the Host's named containment-verifier assertion. Expected policy, source pins, verified runtime facts and unobserved facts must not collapse into one `verified` flag. Do not retain raw Docker environment, secret values, or sensitive source paths in the report.
- Ready: immutable held/run/session/container and launch-pin binding, sequenced same-session idle `ready` with actual names, and fresh safe Docker observation. Label negative observations by observer and interval; Host-side zero is not receiver-side zero. Terminal: require the exact ready digest for every `held_cancelled` and for failures after ready; omit it only on failures without a ready record. Retain the accepted cancel coordinate and its binding to the published ready record, successful close delivery and matching receiver completion, receiver/attach exits, and cleanup disposition. Capture same-session receiver terminal counters applicable to the pinned provider (including local attempts/refusals such as `bridgeCalls` and `forwarderRefused`), and reconcile them with separately identified Host received/refused/entered counts through exit. Missing, inconsistent or nonzero forbidden-attempt evidence fails H4. Preserve failure evidence and cleanup disposition even without readiness.
- Bind observation, destructive cleanup (including failure paths), and every confirmed absence result to the same trusted Docker daemon as launch and the original owned full container ID. A pinned Docker executable alone does not establish daemon identity; retain how effective daemon selection was bound across commands. Never act by name on a replacement. If create is uncertain and trusted identity cannot be recovered, report cleanup unknown; an empty name lookup or arbitrary inspect failure cannot confirm absence.
- Deliver replayable fixture commands, candidate/binary and result digests, sanitized log/receipt paths and matched and missing checks. In the `controlled-proof` build, test ordinary launch **without** the selector: missing required lifecycle gate or hosted transport still refuses before create; ordinary zero-turn completion and EOF retain their existing failure diagnostics and cannot produce held success. Keep non-proof selector refusal separate. Do not label H4 passed based on existing Step 4 or #6069. No implementation or test execution claimed by this plan.

## Manual orchestration: ownership and launch boundary

One coherent Host builder packet (H1–H5) owns the admission split, controller, and cleanup in one isolated worktree; do not split writers across the same state machine. Dev-vertical owns coordination, result collection and the separate acceptance decision. RL's consumer check (R1) runs against the pinned candidate and witness, read-only and separate from Host construction. U3-A retains its existing owner and is not a dependency. An implementation review, if authorized, should start separately from the builder and not substitute RL's consumer check for code review.

Board #6077 establishes the selector boundary and consumer evidence split. Exact CLI spelling and safe field encoding are implementation choices within those constraints; coordinate any actual shared protocol or pin change with RL. Astra reviewed the frozen prior plan only; no builder was dispatched. This plan commits no implementation model or budget. Before dispatch, confirm implementation authority, check root capacity and shared resources, and bind the exact base, scope, result collection and validation to the assignment. If using the same receiver registration without constructing effect capabilities turns out not to be possible, report the exact blocker rather than qualifying a different provider-less tool surface or lifting the hold. Any future activation path requires separate authority and a fresh same-process observation at the transition; no U4-A receipt is reusable as that permit.
