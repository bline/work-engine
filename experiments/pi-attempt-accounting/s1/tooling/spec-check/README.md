# Standalone S1 specification mechanics

Rust1.92.0, isolated workspace; dependency pins match Work Engine. Commands from this directory:

```
cargo run --offline -- check ../.. --generated
cargo run --offline -- render ../.. /tmp/s1-view
cargo run --offline -- impact ../..
cargo test --offline --lib
```

`spec/ck.json` owns definitions; fixed DTOs reject unknown shape, unknown references, missing constructor fields, illegal stage reads, undeclared symbols, gaps/overlaps in finite declared partitions, and stale acknowledged registered dependencies. `spec/ck.schema.json` documents the fixed DTO schema; compiled tooling rejects a changed runtime schema. SERIALIZATION owns the exact `spec/interface.json` projection. Generation writes only the three approved normative views, never oracle data. `check --generated` compares current bytes without writing.

`impact` reports content-and-transitive-dependency SHA256, even without revision bumps. `spec/dependencies.json` registers L/T/R, external gate verification, independent cases, producer witnesses and Module A/B/C consumers. Null acknowledgement means unestablished, printed explicitly; a stale existing acknowledgement fails. The tool cannot create semantic acknowledgements or approve itself.

Guard facts and formula text are declarations, not executable expressions. Presence partitions do not decide pricing. No raw-attempt reducer, solver, arbitrary expression interpreter, I/O production adapter or code generator exists. Checks prove consistency of registered declarations and generated bytes only; omitted conceptual dependencies, financial truth, writer reachability, external trust and all freeze/S2a gates require their separate owners.

Revision7 adds fixed result-bearing financial branches over 540 typed fact tuples (compressed guards), explicit contract exclusions, availability and retention checks, nine finalization bindings, total typed wire projections, primary/validity/auxiliary noninterference boundaries, and nested named-type dependency edges. These checks inspect declarations only. They never ingest raw attempts or compute money. Independent financial arithmetic assertions and source-bound semantic review remain necessary.

## Revision8 supplied-record and schema interfaces

`read_spec` and `validate` enforce the real Draft2020-12 canonical schema, including distinct StageId/BoundaryId domains. `serialize_external_constructor` maps typed constructors to actual external fields (Exposure.pool, High.kind/nano/basis, decimal valuation amounts, derivations and obligation string sources). It performs serialization only.

`evidence ROOT FILE` validates an accounting document shape or a closed `{documents:[...]}` bundle. The bundle checks exact input/result/expected kinds, grant-kind and extent references, unique total origin/base/active ownership, final refinement facts, complete coverage and physical-credit alternative sets. `wire ROOT FILE` validates an attempt fragment or array of fragments containing exposure and optional valuation/obligation/accounting_result_ref. `canonical ROOT FILE` validates the supplied canonical specification. Public APIs are `validate_schema`, `validate_accounting_document`, `validate_accounting_bundle` and `validate_wire_document`.

Budgeted coverage uses an immutable C primary witness. The separately declared `unbudgeted_completion` route uses a computed applicability and completion witness inside AccountingResult, with exact usage origin/valuation references. Expected assertions never authorize release. Supplied witness coherence does not establish raw applicability, actual complete valuation, external grant authority or live provenance; independently authored raw assertions own those bounded checks.

`impact ROOT NODE...` names affected registered consumers. Predicate/type/rule/projection/schema revisions invalidate relevant R/T, contract/schema/wire, Python and independent consumers. Null acknowledgements remain unestablished. The specification owns accounting.schema.json and wire.schema.json through canonical schema nodes and generated projection checks.

Meaningful structural controls are `cargo test --lib --test structural_r8 --offline`; `tests/schema_agreement.py`, `tests/wire_corpus.py` and `tests/evidence_controls.py` compare the actual CLI and independent standard-schema/VC07 inputs. These checks do not implement or qualify a raw financial reducer, interpreter, coverage solver or production adapter. Independent tests remain independently owned and may qualify different claims.

Accepted coverage valuation_ref resolves to a supplied `valuation_records` row with `complete=true`, exact usage_origin_refs and an external wire_ref. Unbudgeted applicability_ref resolves to the separate computed `unbudgeted_applicabilities` table, completion_ref resolves to `unbudgeted_completions`, and both bind the same exact usage origin/valuation. These references cannot point to expected assertions. The raw financial truth of these supplied records remains independently qualified.

## Sole C-validity ownership and exact numeric domains (slice 1b)

`validate` rejects any non-C stage rule whose output constructs a C-owned decision (`SettlementDecision` and any type carrying one in a variant field), with `C-validity owner violation: stage S rule R constructs C-owned T`, and any stage or boundary other than `C`/`C-validity` declaring the `settlement_validity` output. S forwards C's immutable `validity_ref` through the typed `SettlementForward` only. Controls: `tests/c_owner_domains.rs`, `tests/c_owner_cli.py`.

Published numeric/string domains: every `revision` is `1..=4294967295` at the nine integer sites of `ck.schema.json` (`$defs` Boundary, Branch (`decisions[].branches[]`), Decision, Formula, Node (shared by `invariants` and `owner_policies`), Projection, Rule, Stage, TypeDef); input `original_position` is `0..=18446744073709551615` (`accounting.schema.json`); every nano-USD decimal string is the canonical nonnegative decimal `0..=170141183460469231731687303715884105727` (i128::MAX, MONEY/SERIALIZATION; regex generated by `tests/nano_domain.py`) in `accounting.schema.json` and `wire.schema.json`.

No dependency, feature or lock change: `serde_json =1.0.151` keeps default features. Enabling `serde_json/arbitrary_precision` was tried and rejected because it changes `Number` equality for every crate in the test build and breaks the oracle-owned `independent_raw_axes` premise comparison; `jsonschema`'s own `arbitrary-precision` feature needs `jsonschema-macros`, unavailable offline. Instead `numbers.rs::parse_json` (used by the CLI for every supplied document and the canonical spec) reads number literals with exact decimal arithmetic, never via `f64`. `1.0`, `1e0`, `4294967295.0` and `18446744073709551615.0` are the integers they denote and `x.0000…1` is a non-integer. Integral literals within `i64`/`u64` are exact. A value `f64` cannot keep exact (an integer wider than `u64`, or any non-integer) becomes an interned stand-in: equal values share one, distinct values never do, integral stand-ins lie beyond every published bound and non-integral ones are non-integral. Hence `type`, `minimum`, `maximum`, `uniqueItems` and `enum` decide exactly, including at the free-form `Assertion.expected_fields_or_relations` location under `uniqueItems`, and out-of-`f64` literals such as `1e400` neither error in the parser nor panic the validator. Limits: exponents beyond 2^40 in magnitude are clamped before classification, and a diagnostic printing a rejected non-integer shows its stand-in rather than the original literal. Revision ranges are enforced by the published schema plus serde's checked `u32`; the Rust integer reads of `original_position`, constructor `U64` values and the zero-revision test use `exact_u64` (`exact_u32` is a public helper used only by tests). A `Value` produced by the stock `serde_json` parser is read at face value. Controls: `tests/numeric_domains.py` (983 checks incl. Python Draft 2020-12 where Python's float parse is exact), `tests/no_panic_mutations.py`, `tests/c_owner_domains.rs` (includes a differential check of `parse_json` against `serde_json` on every repository JSON file and the free-form `uniqueItems` controls), unit tests in `numbers.rs`.

## Coverage coherence and reference-namespace application (slice 2b)

`validate_result` enforces, per accepted coverage: the monetary origins are exactly the selected inventory (the obligation's primary classes plus its usage origins when budgeted, the completion's usage origins when unbudgeted), anchors are disjoint from them, every cited `definite_link_refs` entry joins a covered anchor to a covered request origin (a link to another request, or an uncited/foreign link, is not this coverage's authority), every anchor has such a cited link, and every `inactive` unit is retired into its `successor_ref` by exactly an accepted coverage listing it (no hold is released without coverage). C-validity witnesses must belong to the covered obligation's primary origins and be `valid`; valuation usage must equal the selected usage inventory. These are structural/typed coherence checks; financial truth stays with the oracle. Controls: `tests/coverage_r2.rs` (synthetic two-request fixture), `tests/coverage_namespace_controls.py` (supplied VC07/VC11/VC08/U06/V03 bundles).

`validate_accounting_bundle_with_payloads` (the `evidence` CLI) additionally compares each origin's initial-contract `reference_namespace` with the raw row it is bound to by `source_revision_ref` digest and `raw_bytes_sha256` (`namespace.rs`). A reservation `usd_reserved.rid` row is `dollar_ticket`; a `subscription_proxy_admitted.rid` row or any row carrying `subscription_proxy.rid` is `admission`. Declaring the other namespace (even when bundle, contract, grant and provenance agree) is rejected; `unestablished` and rows without a reference are not judged; one base may not group origins of both namespaces. Raw rows come from `corpus/cases/<lineage_id>.json` under ROOT or from a payload carrying `original_inputs`; a bundle whose origins are bound to neither (e.g. a mutated subject) is not judged, so this is applicability, not raw admission or a live guarantee.
