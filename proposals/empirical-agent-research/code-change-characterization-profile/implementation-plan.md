# Implementation Plan: Code Change Characterization Profile

This is a possible delivery shape for the formed candidate, not implementation
authority or a mandatory procedure. Phases may be combined, reordered, or
revised when another route preserves exact subject identity, evidence quality,
recomputability, temporal cutoffs, and semantic ownership.

## 1. Freeze representative immutable subjects

Select a small set of existing Work Engine checkpoints that exercise materially
different shapes:

- physically large but semantically narrow;
- physically small authority or invariant change;
- state/persistence/recovery change;
- schema or interface change;
- cross-component change;
- review remediation with at least two candidate attempts;
- UI or rendered-behavior change with and without browser evidence; and
- documentation/configuration-heavy change.

For each subject bind base/result trees, task-owned manifest, patch digest,
plan/scope revision, attempt, checkpoint disposition, and evidence cutoff.
Preserve original candidate and accepted subjects separately.

## 2. Deterministic baseline vertical

Produce a versioned profile containing inexpensive observations such as files,
lines, hunks, file categories, tests, documentation, configuration, changed
symbols, and module/package distribution. Prove deterministic output for the
same immutable subject and truthful distinction among zero, unknown,
unsupported, failed, and not applicable.

Use checkpoint identities rather than reconstructing task scope from the final
working tree. Preserve analyzer version, source hashes, coverage, and exact
derivation inputs.

## 3. Before/after entity lineage

Exercise stable matching across unchanged identity, rename, move, signature
change, split, merge, deletion, addition, and ambiguity. Retain candidates,
method, confidence, and unresolved alternatives rather than forcing one match.
Use direct diff evidence and structural graph evidence according to the claim
each can establish.

## 4. Structural profile

Add before/after call, dependency, interface, module, ownership, persistence,
external-service, concurrency, and trust-boundary observations where supported.
Prove analysis against both immutable repository worlds; a current-only graph
cannot establish a historical delta. Preserve graph project, generation,
snapshot subject, coverage, traversal direction, and limitations.

## 5. Semantic projection

Reference existing architecture, invariant, role, capability, lifecycle, claim,
and proposal owners. Separate a structural relationship from a semantic impact
claim. Model-assisted classification retains prompt/protocol, model, evidence
cutoff, source identities, uncertainty, and classifier version and cannot
silently become direct evidence.

Exercise the five-way distinction among declared intent, observed code change,
claimed impact, demonstrated behavior, and later outcome.

## 6. Profile lineage and composition

Represent original candidate, remediation candidate, accepted checkpoint,
completion commit, and optional slice/campaign aggregates without destructive
rewriting. Demonstrate that non-additive topology, dependency radius, novelty,
and semantic breadth are recomputed over the aggregate subject rather than
summed from children.

## 7. Review Bench baseline enrichment

Enrich a bounded set of existing immutable benchmark candidates with frozen
deterministic profiles. Preserve case admission and truth adjudication as Review
Bench responsibilities. Add task/problem and evidence-availability fields beside
the change profile so code properties do not absorb prompt, claims, graph,
browser, or repository-access differences.

For paired reviewer attempts retain:

- exact reviewer model, harness, reasoning, and environment evidence;
- exact reviewed subject and change-profile revision;
- raw and normalized findings;
- equivalence and adjudication provenance;
- confirmed, rejected, missed, duplicate, and unique findings;
- calibration and verification quality;
- remediation and later outcomes; and
- token, latency, tool, and lifecycle resource use.

Report confidence-qualified conditional observations rather than selecting a
production reviewer from sparse cases.

## 8. Prospective slice capture

At each sufficiently identified slice candidate, freeze the subject profile
before revealing later remediation or truth evidence. Preserve profiles for
accepted and rejected candidates. Join future claim-aware and Codebase Memory
harness variants by reference without rewriting the unaided baseline.

## 9. Correlation and controlled-test readiness

After enough representative cases exist, evaluate which independent change
dimensions correlate with detection, precision, calibration, disagreement,
resource use, and later correctness while controlling for task and environment.
Retain analysis code/version, source case identities, missingness, uncertainty,
and confounders. Treat historical effects as hypotheses for matched or
controlled tests, not causal conclusions.

## 10. Downstream proof

Have at least two consumers use the same profile for different judgments, such
as Review Bench stratification and test-selection analysis. Confirm that each
consumer can choose different relevant dimensions without changing the profile
contract or requiring a universal score. Recompute the profile with a revised
analyzer and show that original subjects and earlier derived revisions remain
addressable.
