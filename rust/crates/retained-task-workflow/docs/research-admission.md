# Research input admission

The task owner retains task/request preparation heads, immutable basis bytes,
notices, saved adoptions and reconsideration obligations in schema 3. Opening an
exact schema-2 store migrates it in one transaction, retaining its identity and
all previous task/command/operation/effect bytes. Interrupted migration rolls
back. Recognized schema-0 bootstrap and explicit stopped schema-1-to-2 migration
remain supported; arbitrary old or altered schemas refuse.

Nomination guards fresh ordinary submit variants before any preparation exists.
Historical ordinary duplicates remain readable. Caller facts cannot occupy
`research-` sources. A checked research adoption adds canonical basis metadata
under that reserved prefix; its basis, immutable input, exact lifecycle command
and receipt commit under the existing owner transaction. Preparation revision
is independent of task, cursor and lifecycle revision. Adoption hashes the full
submit, key, expected preparation revision and basis digest under a separate
operation domain. Historical duplicates return their original receipt before
consulting the current head.

Capabilities are opaque, store/key/role bound and never deserialized. The narrow trusted-startup notice constructor requires an externally admitted
host/source/protection consequence; Rust visibility and association data do not
authenticate a caller. Only `controlled-proof` exposes synthetic producer and
basis qualification constructors. These fixtures do not establish
research judgment, actual consumer delivery, installation protection or A5
execution. The owner validates retained bytes and exact internal bindings;
production basis verification remains unavailable while C1 actual delivery is
unestablished.
Research notice selectors start with `research.`; decision/operator selectors
start with `decision.`. The trusted preparer registers the complete selector set
before either a notice or readiness can be published.

A notice increments and blocks the head, including before first preparation.
Only changed checked dependency revisions can resolve it. A committed notice
before adoption rejects the old revision. A later notice retains the original
input/command and adds an exact adoption reconsideration obligation. It does
not revoke a grant or imply execution cancellation. No cross-store atomicity or
observation of unreported outside changes is promised.

The fixture contract bounds identifiers to 128 bytes; a task to 16 request keys
and 64 adoptions; a basis to 256 dependency pins, 128 immutable members, 128 KiB
metadata and 8 MiB retained bytes; a key to 256 checked preparations and 1,024
detailed notices. Existing stricter submit/locator/text bounds still apply.
A complete query reads at most 64 rows and refuses on a 65th. Detailed notice
exhaustion atomically blocks the head and retains one bounded digest marker;
subsequent work requires owner disposition. Revision overflow permanently blocks
admission. Capacity refusal never returns a partial complete result.

Controlled fixture revision pins equal the SHA256 of the referenced dependency
artifact bytes. The retained result artifact is typed JSON with `dependencies`
(the full exact pin map) and `text` (advisory recommendation text). Missing or
mismatched bindings refuse, including when a notice predates every preparation.
Changed retained inputs plus a newly bound recommendation can resolve that
notice. Canonical material retains the advisory text and exact result digest;
these checks do not authorize an issuer or establish research judgment.

Retained recommendation JSON rejects duplicate object keys, including identical
or conflicting selectors inside `dependencies`. Preparation and adoption use
the same typed decoder; strict outer fixture parsing does not substitute for
checking embedded artifact bytes. Refusal publishes no input, command or adoption.

The controlled installed-notice path adds an optional `admission` association to
new notice receipts. It records the controlled current startup, upstream
installation/configuration/admission, operation manifest/admission, caller
evidence, exact operation/role and payload digest in the same notice transaction.
The association is data, not an authority permit. Trusted host composition supplies the production association; the controlled
constructor is feature gated and labelled synthetic. Both check store/key/role
and exact notice digest, and grant neither preparation nor adoption. Historical retries
return the original stored receipt even if later evidence differs. Absent
associations stay absent when serializing old receipts; schema 3 and existing
saved basis/input/command identities remain unchanged. Controlled installed-key
setup uses one owner transaction for nomination and selector registration, so a
registration refusal cannot publish a partial nomination guard.
