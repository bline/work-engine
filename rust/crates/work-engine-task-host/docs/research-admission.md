# Controlled research admission seam

Optional trusted startup `research` nomination names the audit task and subject.
It guards fresh ordinary submission before first preparation, while the task
owner independently guards every library submission variant. Native task
operations have no research producer capability.

Ordinary default startup supplies no research producer. Fresh
`research.prepare.v1`, `research.invalidate.v1` and `research.adopt.v1` refuse
without admitted installed or controlled qualification evidence. Scoped `research.read.v1` and
`research.read_adoption.v1` retain readback, including recovery-only operation.
Request/response framing retains the existing 128 KiB envelope and strict JSON
parser. Artifact payload bytes stay outside RPC.

With `controlled-proof`, nomination may explicitly name `controlled_fixture`,
a private file containing version 1 `ControlledFixture`. Its exact bounded
basis variants and notice payloads are loaded once, checked before nomination
publication, and retained in memory. DTO labels cannot select producer roles or
expand these inputs. Successful responses say `qualification: controlled_only`.
The fixture is synthetic evidence, never a production protection/authority or
actual A5 delivery claim. No inference runner is added.

Fresh adoption obtains existing lifecycle preflight outside the owner lock,
then commits through the typed task-owner seam. Existing lifecycle revision and
grant fences still apply. Historical duplicates use their exact saved command;
selected-host unknown reconciliation follows the existing policy and cannot
rebase to newer preparation, context or grant. Recovery-only refuses fresh
mutation and reads saved receipts; later invalidation does not automatically
adopt again. The controlled owner-commit cut remains available for crash/retry
qualification.

Controlled fixture revision pins equal the SHA256 of the referenced dependency
artifact bytes. The retained result artifact is typed JSON with `dependencies`
(the full exact pin map) and `text` (advisory recommendation text). Missing or
mismatched bindings refuse, including when a notice predates every preparation.
Changed retained inputs plus a newly bound recommendation can resolve that
notice. Canonical material retains the advisory text and exact result digest;
these checks do not authorize an issuer or establish research judgment.

The complete selector count, identifier syntax and supported `research.` or
`decision.` prefix are checked before durable nomination. Unsupported-selector
startup refusal preserves the store and subsequent ordinary handler submission.

## Installed research and the trusted operator ingress

Ordinary `serve --startup` and `serve --selected` do not admit an installation.
An installed configuration on either route refuses before opening/mutating the
stores. The production-compiled trusted operator route is:

```
work-engine-task-host serve --operator-research-installed SELECTION OPERATOR_INPUT
```

Its Rust entry is `serve_operator_research_installed`. It is a trusted startup
operation, outside all native/tool/socket request surfaces. **The invoker must
already have established the actual authenticated user's approval of each exact
manifest and independently attributable current protection evidence.** The user
selected explicit approvals in the Codex conversation, with Codex as operator
installer. Calling the entry, selecting a flag, supplying JSON, matching a UID or
checking pins does not itself establish those external facts. No production
installation or owner/research decision has been supplied by this implementation.

`research.installation` contains a version-1 `InstallationSelection`: a protected
root and exact pins for authority installation I, authority admission R_I,
upstream configuration C, operation manifest O and operation admission R_O. The
loader checks strict duplicate-key JSON; version/kind/role/key/full payload joins;
one key/two approval roles/16 exact intents; bounded metadata/member counts; and
acyclic references. C compares the complete serialized current HostStartup,
removing only the explicitly downstream `installation` and
`controlled_installation` selections. Every other field, including future added
fields, compares. Notice-only intents require no basis. Preparation uses
`research_digest("prepare", payload)`; adoption/notice retain existing codecs.
No production basis is constructed: C1's complete actual model-input observation
remains unavailable, and installed preparation/adoption refuse.

The selected startup retains exact S/selection bytes and digests. Its strict
version-2 OPERATOR_INPUT pins I/C/O, R_I/R_O, exact approval-source members,
protected root and the owned-native observer policy. It contains no native PID,
future-process protection receipt, caller-authentication flag or deserializable
permit. V1 is refused on this unaccepted production route. The external Codex
operator caller contract still owns actual exact-byte authorization; parsing,
UID and digest checks establish data correspondence only.

Before startup locks, intents, stores or child creation, host staging calls the
research owner's pure `validate_installation_records` and retains its private
checked value with descriptor-anchored artifact bytes. The later trusted
constructor consumes that value rather than discovering old record defects after
startup effects. Immutable artifact contents and mutable owner-store identity
have separate currentness checks.

Lifecycle creates its actual child and performs non-inference initialization,
effective-config readback and thread binding. A trusted in-process one-use
`PendingNativeStartup` handoff holds that runner before every turn entry,
including initial rehydration. Early native tool effects refuse during the hold.
The host joins the owned observation to exact S/selection/config/current host,
installs scoped research producers, then awaits activation acknowledgment before
serving productive requests. Dropped/cancelled endpoints use normal lifecycle
shutdown and runner cleanup. Installed `StartSuccessor` currently refuses before
new thread creation: the old thread-bound evidence cannot admit a successor.

The host-side observer uses the harness's actual child/pidfds and rechecks current
process/root, mounts, reachable protected objects, descriptors and subtree. It
never accepts a nominated PID. Ambiguous or unavailable observations refuse.
Fresh notices repeat currentness; exact historical receipt retries retain their
original association even after the realization is gone.

Production activation is currently unavailable: lifecycle's startup publisher
explicitly refuses without a qualified native-protocol tool-installation evidence
contract. The retained thread request/success acknowledgment is not independent
proof of the installed tool surface. This is an implementation prerequisite under
the native-protocol owner, not merely an absent live approval or C1. C1's final
post-compilation model-input observation separately remains unavailable; fresh
production prepare/adopt still refuse. Controlled tests qualify mechanics only.

Installed v3 restart independently validates complete C2 against current S2 and
C1 against S1. A pure replacement proof preserves I/R_I/root/authority/full finite
intents, permits fresh C/O/R_O member pins, and leaves every other startup field
in semantic equality by default apart from the four existing native restart
identities. Fresh authorization of the completed successor remains external.
Old bases, receipts, commands and their original admission associations are not
rebased or rewritten.

Only downstream of that private consequence does trusted host composition call
the narrow research/task owner installer entries. Research Installation remains
non-deserializable; its exact-use consumer still verifies actual pinned Git
approval objects, bundle/request/decision revision/disclosure scope, qualified
records and role-specific issuers. The task producer is store/key/role/exact
payload bound. Its notice and current admission association commit in the same
task-owner transaction. Historical notice retries return the original receipt,
including when a current realization is gone; changed payloads cannot rebase.
No new producer capability appears on the native or ordinary request surface.
Rust API visibility is not external caller authentication: the owner entries
explicitly require trusted composition, like the existing nomination boundary.

One pinned directory descriptor anchors single-component member reads without
following symlinks. Private owner/mode, single-link identity, size/digest and
changes during reads are checked before bytes are retained. Bounds are 128
members, 128 KiB per metadata record and 8 MiB total. Root aliases, native-root
overlap and snapshot disclosure of protected bytes refuse. These necessary
checks supplement the actual externally established protection observation.
Hostile trusted-UID processes and compromised installer/host/kernel remain
excluded. Source integrity alone establishes no protection claim.

With `controlled-proof`, mutually exclusive `research.controlled_installation`
exercises the same records through explicitly synthetic installed notice
producers. Default builds reject that input. Older `controlled_fixture` remains
separate. Controlled outputs/associations say `controlled_only`; its startup
digest names the reserialized fixture startup. An internal test-only classification registration can exercise the full selected
entry with synthetic authorization/observation provenance; it cannot nominate a
child or skip the activation/currentness gate. These controls qualify mechanics,
never actual authentication/protection/A5. A real admitted invocation instead retains
exact selected S/selection identities and current host evidence. Key setup is
atomic with nomination. Schema 3, historical serialized records, saved commands,
notice ordering/reconsideration and existing controlled basis behavior remain.
