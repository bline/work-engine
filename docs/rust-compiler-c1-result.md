## Oracle and compatibility

The five immutable structure/interface fixture pairs and producer-neutral expected IR remain under `rust/crates/work-engine-compiler/tests/fixtures/v1/`. `cases.json` SHA-256 is `8bbc6ca3bff468f47895229692b47d1d7e5ad3e4cbfb1bacac5ec91cadc4b43c`. They were captured from pinned `app-server/src/skill-compiler.mjs` SHA-256 `abb2cdf31c2d6a2f4a19dfc062cbaef6b96ece6fd74721b0bf170dd5ef23cbeb`, Node v22.23.2, YAML 2.9.0 and `verifySources: false`; P-BLD uses immutable `7583e209:skills/slice-builder/SKILL.md` bytes. Executed Rust tests compare each Markdown output byte-for-byte and compare IR after excluding only the accepted producer-identity delta, `work-engine.skill-compiler.rust-v1`. All five pass. Runtime requirements remain `verified_sources: false`; no caller-supplied verified flag exists.

The parser tests cover duplicate keys and aliases, unused anchors, multiple documents, tags, merge inputs, BOM, numeric `1.0`/`1e0` schema values, Unicode, exact YAML null/boolean spellings, scalar mapping-key conversion and non-finite scalar keys. In an open `observation_limits` map, `nUlL` and `TrUe` remain strings; `.inf`, `-.inf` and `.nan` keys become `Infinity`, `-Infinity` and `NaN`; null keys become empty strings and fail the text validator. Non-finite values fail validation. JavaScript UTF-16 ordering is exercised by the U+1F600/U+E000 list vector (requirements digest `ca5b7a465617631ae6e97a53bd267f45707728a812859d014a9813b6e902ee15`). Exact numeric/escaping codec vectors and deterministic repeated output pass.

Executable C0 S04/S13 vectors use the exact pinned Node v22.23.2 / YAML 2.9.0 oracle identified above. A leading UTF-8 BOM on either P-SUP YAML source is admitted and leaves compiled Markdown and semantic IR unchanged, while retaining its changed raw input SHA-256 (`0e1f2062b13e2581e4a0e4072ec2d17365a662d0b50f25690f5a509f97595f18` for structure; `9869c5eee1b45bdb9e66854e4f2ca7e7616470f9b1cef1c56aecb75f4f6abbe0` for interface). The first Rust test exposed a real yaml-rust2 divergence: the parser included the leading BOM in `schema_version`. C1 now removes only the leading BOM from the text passed to the parser and continues to hash the original source bytes. Both BOM vectors pass.

In P-SUP's open `observation_limits`, the pinned oracle admits quoted `'<<': bounded` and plain `<<: bounded` as the same literal scalar key; Rust matches the resulting `"<<": "bounded"` projection, output bytes and the distinct raw input digests. The oracle refuses `<<: *defaults` when alias resolution is disabled; Rust returns `invalid_yaml`. For `<<: {a: b}`, the oracle reaches the nonempty-text validator and refuses the mapping value; Rust returns `invalid_structure`. These are distinct tested paths: C1 does not reject a valid literal `<<` scalar key merely because alias-based merge input is refused.

The user accepted one explicit C1 input restriction in coordination-board message 1167: scalar YAML mapping keys remain supported; array/object collection keys reject as `invalid_yaml`. Legacy YAML 2.9 accepts and presentation-stringifies those keys. Both collection shapes have executed rejection assertions. This is the only accepted admitted-input delta claimed here; C1 does not authorize later consumer cutover.
