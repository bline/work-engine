# RP2 initial-only permanent-host validation

This implementation follows the accepted RP2 plan v4 (`80d067d96f927e0aa2ab09e03f709e4abd748d35d4fd34c1f01b4d54d8c7c5e1`). Its result is an offline mechanism qualification. It does not install a production acceptance pin, read production credentials, call an installed provider, establish an initial Claude observation, authorize retained entry, or complete a review campaign. Those decisions and observations belong to RP3 and SC3-H.

The permanent host accepts a separate qualified startup envelope. The controlled schema-1 route keeps its own profile and custody checks. A qualified schema-4 campaign requires the independent protected deployment pin, exact accepted source, selected candidate and claim pair, runtime profile, binary/catalog/CBM and credential *metadata*, session and attempt, and strict aggregate 64 MiB resource policy. The campaign issues a private fresh-origin entry only from a newly Applied dispatch under its owner gate; recovery and replay carry descriptive records only. E1 consumes that entry after exact scope binding and creates its private one-use initial permit. The offline test pin and offline entry have distinct types and cannot become installed authority.

The Applied entry carries the exact campaign-dispatched episode and request, candidate receipt/commit/tree/patch, accepted static prompt template and attempt horizon. E1 recomposes the prompt from that template and request before intent; a mismatched episode, candidate, prompt or horizon refuses without peer entry. Custody retains two different profile identities: the physical code-change profile for campaign and CE admission, and the executable/model profile for Claude readback. Historical RP1 prepared records omit the latter and retain their legacy fallback. Qualified startup uses campaign's dynamic schema-4 gate validation, while the controlled SC0 route retains its pinned historical gate.

The RP2 selected-snapshot check compares every reviewer-exposed source file and directory, regular-file bytes and executable mode against the selected Git tree. It rejects dirty tracked files, a wrong checkout, extra exposed files or directories, links and special files before candidate-private indexing, on frozen startup and immediately before E1 launch intent. The reviewer mount hides Git administrative data, which is outside the selected source tree. This is a bounded, repeated readback of an immutable candidate expectation; it is not a claim that an independently writable host checkout has become a kernel-atomic snapshot.

The installed deployment registry path is `/etc/work-engine/review-host/deployment-pin.json`. Its selected acceptance source and every ancestor must be canonical and root-owned, with non-writable directory ancestry and a root-owned read-only-to-unprivileged file (mode `0644` or `0444`). The qualified installed startup document has the same protected-owner and readable-mode requirement; an unprivileged caller cannot substitute an arbitrary prompt or role document. These files contain nonsecret acceptance/startup metadata. The configured permanent host may run unprivileged; RP3 must supply the actual registry, accepted source, startup and model. Neither a startup JSON field nor a fixture can mint the installed pin. Credential source validation at startup uses metadata only. E1 reads a credential only after fresh Applied entry and guarded preflight; the offline qualification uses a task-owned canary.

The frozen CBM boundary publishes an immutable candidate/index manifest once and reopens it without reindexing or provider launch. The candidate digest includes the bytes of opaque binary assets. CBM's coverage check excludes its explicitly ignored `.bin` assets and Git administrative metadata; the manifest records the checked indexed paths and coverage response, with the graph's best-effort caveat. A changed candidate, store/config/MCP/coverage sidecar, manifest, pin or selected identity refuses. The qualified host keeps one domain worker and an independently responsive status control loop.

RP1's strict 64 MiB aggregate session storage/process cgroup and zero-swap realization remain the RP2 runtime policy. No larger provider memory allowance is inferred. A real installed Claude build may fail this policy; that is an unqualified installed profile until a separate owner decision and hostile proof establish a different enforceable budget. RP0's 4,096-request relay behavior and hard cleanup deadline remain unestablished.

The feature-gated offline host fixture starts the actual permanent binary, passes one campaign Applied entry into E1's guarded peer, and records an out-of-journal witness when the peer calls the candidate-private CBM relay after receiving its prompt. It intentionally receives `ControlledFixture` custody. The production reader and J1 join reject that class, including on cold recovery; no test result is relabeled `QualifiedProvider`. A separate test-only adapter injects a synthetic controlled fixture owner into the same host J1/J2 join with a separate fixture claims root. It checks false/unestablished and established findings routes and owner-stage recovery without granting installed authority. For the 700 status probes, the offline peer first receives the real CBM `index_status` response, then requests a fixture-only hold on that same relay socket. The relay syncs an entry marker before blocking its reply. The host begins probes after observing that marker, requires every status to report busy, then syncs a release marker only after all 700 replies and at least six seconds. The relay syncs its exit marker before replying to the peer. The test records all events on one host monotonic timeline, the raw latencies, zero timeout/error counts and the single peer witness; it rejects an early peer result or an exit before the release. This mechanism is absent from an ordinary build and does not expand the production CBM allowlist. Candidate-one aggregate and candidate-two raw samples predate this handshake and do not establish the same held interval. A separate fault gate killed the first host after checked episode begin, then cold recovery returned `unresolved` with `launchAuthorized=false`; replay did not enter the peer. These fixtures prove local host responsiveness and one local guarded peer prompt, not a live provider or remote at-most-once effect.

The separate RP1 guarded isolation regression initially timed out in a real cold CBM RPC with its historical ten-second fixture horizon. An intermediate diagnostic measured 56.672 seconds from E1 entry to capture. The final fixture uses a 120-second horizon for its real-CBM cases, within the accepted ten-minute attempt maximum; this changes only the test's scheduling margin. The first failures and the diagnostic run remain in the private gate packet. They do not establish a hard cleanup deadline or justify skipping the guarded quota and hostile-write assertions.

The inherited `code-change-profile` analyzer expects SHA-256 `1b814da3…` of the historical `slice-checkpoint` validator, while the repository baseline contains validator SHA-256 `398086bb…`. Eight schema-4 downstream tests fail before their owner logic on this helper binding. Their qualification-only overlay replaces that single helper with the exact analyzer-pinned historical version; all RP2 paths, lock bytes and other helper bytes match the candidate. Overlay passes must be labeled separately, and the unmodified baseline failure must remain visible.

Qualification is bound to the exact source/lock manifest and raw gate receipts in the private RP2 implementation packet. The test matrix includes default and fault-enabled debug/release E1, campaign, workflow and host suites, focused frozen-index and offline authority tests, affected CE/episode/J1/J2 regressions, all-target Clippy, formatting and locked Cargo metadata. The preexisting expensive SC3-D 100/101 debug case is identified explicitly when excluded and receives optimized capacity proof. Any failed or infrastructure-limited run remains a failure receipt until a successful exact-closure replacement is recorded.
