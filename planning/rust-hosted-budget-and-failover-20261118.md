## Goal

Hosted Work Engine jobs should move between authorized funding routes, and pause and resume, **deterministically from recorded quota and credit state**. Agents do not manage budgets, choose payers, or decide when to resume. For every route the system should know whether it is usable now and, when it is not, **when it will be usable again**: the 5-hour, weekly or other window reset for subscription quota; never, until the operator acts, for exhausted API credit.

### Operator decisions (2026-11-19)

- Objective budgeting is out of scope. No objective grants, spend/headroom computation, or composition with `metrics/scripts/usage_ledger.py`; the Python tooling is untouched. Runaway work is handled by escalation rules and timeouts, a separate concern. Resource allocation may be planned later.
- Behavior stays deterministic. Model judgment remains only in the semantic part of a pause: what state to preserve and how the work resumes.
- OpenAI and Anthropic expose no API for remaining API credit (OpenRouter does; see the OpenRouter lane below). For OpenAI and Anthropic routes, credit exhaustion is known only from refusals.
- Track when quota or credit becomes available again, not only that it ran out: after failover to API and API credit exhaustion, the system must know when it can fall back to subscription quota; a pause must know when to start again.
- Act before quota runs out, not only on refusal: an operator-set low-quota threshold per window triggers preparation (state preservation or an early switch). Quotas reset at any time relative to running jobs, so switching early and failing back after a reset both happen **within a running job** where needed, through one router change: a deterministic decision input before each send.
- Classify non-success response heads in the Host relay before relaying, so a pinned credit-exhaustion or overload shape fails over within the request. A failure that arrives after a successful (200) head has already reached the container: it is not failed over within that request; the next request may switch.
- A route with no evidence yet (`unknown`) is sent to; that send verifies it. It never pauses.
- Resume is owned by a deterministic job scheduler in the hosted runtime (not the repository's role-scheduler skill, which by contract does not activate work). The lifecycle controller owns state preservation and the continuation the new job starts from.
- Round 4 answers: (1) failures after a 200 head switch at the next request, the stream is never buffered; (2) classification reads use a small budget inside the existing head window, not a larger window; (3) the classification table's digest is bound in the runtime admission next to the route-table and catalog digests; (4) preservation after a low-quota signal runs on another policy-allowed route or without inference, never on the low route.

## Starting point (verified by the independent review unless marked)

- **Router.** `pi_route.rs` fails over a fixed model between routes in the job's admitted table only after a definitive head refusal (401/402/403/429, nothing relayed). It never substitutes models, never retries uncertain attempts, and a proactive skip needs a new policy. Every admitted route is built authorized and unrevoked, so a subscription-first/API-fallback table is standing permission to spend API credit after a subscription refusal. The table is pinned by `hosted_routes_sha256`.
- **Job lifetime.** Every hosted job is far shorter than any quota window: relay jobs at most 3600 s, other profiles at most 300 s. The router is per Host process and a refused route stays unavailable for the rest of the job (stable routing, `pi_route.rs:95-97, 137-146`). Today, therefore, a job that failed over stays on the fallback route until it ends (up to an hour), even if the subscription resets meanwhile, and nothing acts on low quota before a refusal. Resume after a pause always means a new admitted job. This plan adds within-job switching through a router decision input (slice 3).
- **Journal.** Every hosted job, whatever started it (lifecycle relay via `pi_host_serve`, server-run coding, analysis-profile jobs launched by the H2 route job writer through `analysis-qualification`), writes the Host journal `pi-state.json` with per-request attempts, dispositions, routes, payers and digest-bound retained artifacts. This plan reads the journal and its artifacts for all hosted jobs; per-turn captures are a projection of the same journal and are not needed except for the relay profile's turn-level time bound. Journals live in per-job state directories with no registry, so the view takes the set of journal roots as an explicit input.
- **OpenRouter lane (in progress, branch `openrouter-lane-20261119`, not merged).** It adds a third wire, `Wire::Completions` (OpenAI `chat/completions` via OpenRouter), to the same Host files this plan changes. The lane authorizes a bounded DeepSeek measurement arm, not a standing hosted route; if an OpenRouter route is admitted under this plan's policy, every allowlist, classification entry and gate here gains a Completions/OpenRouter row. OpenRouter reports remaining credit through its API (operator statement; endpoint and semantics to be confirmed in slice 5), so on that route API credit becomes a readable dimension with an observation time: it can trigger the low-quota prepare action before exhaustion. A reading is still an observation, not a reserved balance; concurrent spend between reading and send is not fenced. The poll needs the route's key, so the Host transport owns it and retains each reading as a timed, digest-bound journal artifact; the read-only view consumes only that artifact, and no artifact means credit `unknown`. Implementation of this plan rebases onto the lane after it merges.
- **Funding classification.** A route's endpoint kind (for example `https:anthropic-oauth` vs `https:anthropic-api`) distinguishes subscription from API funding; the transport refuses a kind/endpoint mismatch; `journal.coding.hosted_transport.payer_sources` is the cross-check. Neither is an account identity; whether two payer names share an upstream account is an operator declaration.
- **Retained quota evidence.** `pi_stream::kept_header` keeps `request-id`, `anthropic-ratelimit-*` and `*overage*` headers, written to `relay.json` `headHeaders` only for relayed (successful-head) attempts. Refused attempts retain only the refusal body (`http_status`, `refusal_body_sha256`); crash-reconciled attempts retain only their stream. **So at the event failover acts on, no rate-limit header, `retry-after`, reset time or head time is retained today.** No OpenAI/Codex rate-limit header is kept on any attempt.
- **Definitive refusals.** Only 401/402/403/429 at the head with nothing relayed are refusals the router fails over on. Any other non-success status (for example a possible 529 overload, or credit exhaustion if a provider signals it another way) is relayed to the container and settles `Uncertain`: the reservation is held, there is no failover, and the job fails. Its headers and body are retained (`relay.json`, `stream.sse`), so the view can classify it after the fact. Which status each provider uses for credit exhaustion and overload is not established in the repository.
- **Header names (not verified in this repository).** Anthropic's unified rate-limit headers are believed to carry per-window utilization and reset fields (5-hour and 7-day) beyond the `-status`/`-overage-status` fields the existing guard reads; the Codex subscription backend is believed to send primary/secondary window usage and reset headers (the Python ledger reads analogous `rate_limits` windows with `window_minutes` and `resets_at` from Codex CLI rollout events, parsed at `usage_ledger.py:375-380`; those are Codex's own records, not HTTP headers). Exact names, units and semantics must be established from provider documentation and retained live evidence before use.
- **Time.** The only attempt-level time is `relay.json` `upstreamEndMs` (fallback `openedMs`). Attempts are strictly sequential per job, so other attempts are bounded by neighbouring relayed times and the job's process start; on the relay profile the capture's `observed_unix_ms` adds a turn-level upper bound. Slice 1a adds a head time to refused attempts.
- **Per-job reservations.** The Host reserves catalog estimates per attempt against the job's `budget_microusd` and holds uncertain attempts. These stay as they are; they are not a quota or credit signal and not an account balance.
- **Lifecycle.** The hosted Pi path has no qualified successor or resume path: the lifecycle Pi runner refuses a startup hold and a successor; the receiver's `bridge_replace` is not a hosted successor.

## Model

### Route availability state

For each (payer/pool, quota dimension) the system keeps a state derived deterministically from journal evidence:

| Field | Meaning |
| --- | --- |
| scope | operator-declared pool the route's payer belongs to; routes sharing a pool share state |
| dimension | e.g. subscription 5-hour, subscription weekly, API request/token rate, API credit |
| status | `available`, `exhausted`, `reset_elapsed` (recorded reset passed, not yet verified), or `unknown` |
| utilization | last reported share, when the provider reports one; never inferred from catalog prices |
| low | utilization at or above the operator's low-quota threshold for that dimension (`true`/`false`/unknown) |
| available_again_at | reset time for that dimension; `null` with reason when unknown; API credit has none (`operator_action`) |
| evidence | attempt identity (job, request, ordinal), route, observation time, source header or refusal classification |

Rules:

1. **Observations** come from kept rate-limit headers and `retry-after` on successful and refused attempts, bound to attempt identity and head time, and from classified failures. Relative values (seconds until reset) are converted using the head time; without it, `available_again_at` is unknown. A header without a parseable reset leaves `available_again_at` unknown. Stale, malformed or conflicting readings yield `unknown`, never `available`.
2. **Classification** is a pinned, versioned table from (provider, wire, HTTP status, error type/code) to dimension: subscription quota exhausted, transient rate limit, API credit exhausted, overload, authorization failure, or unclassified. Inputs are both definitive refusals (`refusal.body` plus retained headers) and `Uncertain` attempts with a non-success status (`relay.json` plus `stream.sse`). Unclassified failures mark the route `unknown`, not exhausted for a guessed window. The table is provisional until slice 5 establishes the real shapes.
3. **Exhaustion** sets `exhausted` with the dimension's reset time when known. When that time passes the route becomes `reset_elapsed`; the next attempt verifies it (success → `available`, refusal → `exhausted` with the new reset). API credit has no reset: it stays `exhausted` until the operator clears it.
4. **Shared scope.** Exhaustion observed by one job applies to every job whose route the operator declared in the same pool. Pool membership is an operator input, not inferred. A false declaration makes other jobs skip or pause on evidence that is not theirs, so a proactive skip **to a paying route** on another job's evidence is a separately policy-gated action, and the exposure report covers it. Likewise a pause based only on another job's evidence first makes one verification send on the route (it is treated as `reset_elapsed` for this job); only this job's own refusal or a matching observation pauses.

### Failover policy

An operator-authored, versioned policy maps route state to an action. It contains only routes already admitted in the job's table. Fixed semantics:

- `available`, `reset_elapsed` and `unknown` are **send-permitted**. `unknown` is the cold-start state; sending is how it gets verified. The router's refusal path still applies.
- `available` but **low** (at or above the operator's threshold) triggers the policy's **prepare** action for that route: switch early to the next allowed route, or request state preservation so a later pause is clean. The policy names which. Preservation that needs inference runs on another policy-allowed route or without inference, never on the low route. Prepare cannot guarantee completion before exhaustion: one large request can cross from below the threshold to exhausted. Thresholds are set from slice 5's observed per-request utilization deltas, leaving at least one such delta of headroom.
- `exhausted` with a future or unknown `available_again_at` is **skip**.
- **Pause** only when every policy-allowed route is `exhausted` (or low with a pause-on-low policy).

Example: subscription first; at 90% of the 5-hour window, request preservation; when exhausted, API; when the subscription's reset passes, return to it; if both are exhausted, pause until the earliest `available_again_at` among policy-allowed routes (after API credit exhaustion that is the subscription reset).

The policy is evaluated **at job admission or resume and before each send**. Quotas reset at any time relative to running jobs, so switching early, failing back after a reset and skipping an exhausted route all happen within a running job through **one router change**: before each send the router accepts a deterministic decision input bound to the job, its route table digest, the policy version and the state observation. The input can select only routes already admitted in the job's table, never a fabricated refusal, and never resends an uncertain attempt. A route the router saw refuse becomes eligible again only on a bound observation that its reset has passed, and at most one verification attempt per reset observation per request is allowed, so a route cannot burn the request's attempt budget oscillating between `reset_elapsed` and refused; per-request and per-route attempt limits still apply. Each decision is journaled on the attempt as `{policy_version, table_digest, state_observation_sha256, action}`, and `Router::recover` requires it for any route change not preceded by a refusal. An input is **stale**, and ignored in favor of the router's default, when its observation is older than the route's own latest attempt in this job or older than an operator-set bound. The view's state reaches the Host as a digest-bound artifact (a slice-3 deliverable). No agent chooses a route.

**Non-refusal failures.** Classifying before relay changes three decision points, each named for slice 3: (a) `pi_stream` gains a hold state: a non-success head is held, its body drained and screened within a classification budget (at most 5 s and 64 KiB, counted against the remaining head window), then either treated as a refusal or replayed to the container byte-for-byte as today; (b) the ledger's HeadRefusal release rule accepts table-classified statuses under the same guard (nothing relayed, drained and screened); (c) the router's `Refused` source includes table-classified heads. The classification table is a Host input, so its digest is bound in the runtime admission (next to `hosted_routes_sha256` and the catalog digest) and recorded on each attempt: the same bytes with the same table digest always produce the same disposition, and an absent table or digest mismatch relays as today. An error body that exceeds the budget is unclassified and relayed. This is safe because an error head carries no model output and nothing has reached the container. A failure **after a 200 head** (an SSE `error` or `response.failed` event) remains `Uncertain` as today: content may have reached the container, so it is never failed over within that request; the request ends, the view classifies it afterwards, and the next request may switch through the decision input. Whether a provider signals overload as a non-success head or as a post-200 stream event is established in slice 5.

The plan reports **API exposure**: when an admitted table lets subscription exhaustion spill over into API spend.

### Pause and resume

- A pause records the resume time: the earliest `available_again_at` among policy-allowed routes, which route and dimension it waits for, and the evidence. After API credit exhaustion with subscription exhausted, that is the subscription reset. If no reset time is known, the pause records `resume_time: unknown` and notifies the operator; it does not guess.
- The pause preserves state under the existing state-preservation and recovery contract; pending effects are not replayed.
- A durable, deterministic timer restarts the work when the resume time passes. Since every reset outlasts every job, resuming always means admitting a new job (with fresh state from the preserved continuation). The first attempt after resume is treated as verification: if refused again, the work pauses again using the new refusal's reset time.
- **Owner:** a deterministic **job scheduler** in the hosted runtime owns the durable timer and admits the new job at the resume time. It is not the repository's role-scheduler skill, which by contract reminds supervised roles and does not activate work. The lifecycle controller owns state preservation at pause and the continuation the new job starts from. The hosted path has no qualified resume/successor seam today; establishing one is a slice 4 prerequisite.

## Ownership

| Owner | Responsibility | Not its responsibility |
| --- | --- | --- |
| Host transport and journal | Retain rate-limit headers and refusal evidence for every attempt; classify non-success heads against the pinned table before relaying; keep attempt identity, route and disposition; enforce per-job reservations. | Interpret quota across jobs, choose routes beyond the admitted table, resume work. |
| Route availability (proposed Rust owner; placement for review) | Derive per-pool, per-dimension state and reset times from journal evidence and the refusal table; answer "usable now, and when again". Read-only over journals. | Hold credentials, change dispatch by itself, budget, or infer account identity. |
| Failover gate and router | At admission and before each send, apply the operator policy to the current state; send, switch, fail back, prepare, or pause; the router accepts the bound decision input. | Author policy, raise limits, or retry uncertain attempts. |
| Lifecycle/controller | Preserve state on prepare or pause; supply the continuation a resumed job starts from. | Choose routes, interpret billing, own the timer, replay unresolved effects. |
| Hosted job scheduler | Hold the durable resume timer; admit the new job at the resume time. | Choose routes, decide what to preserve. |
| Operator | Pool membership, failover policy, low-quota thresholds, clearing exhausted API credit. | — |

3c. **Class-based route retention and network outages (operator decisions 2026-11-20).** Supersedes slice 3's "a refused route is never re-eligible without a bound reset observation" for overload and rate limits.
    - Evidence: OpenAI's error-codes and rate-limits guides and `openai-python` (`_base_client.py`, `_constants.py`), fetched 2026-11-20: overload is `503` `service_unavailable_error`/`server_is_overloaded`; follow `Retry-After` (a minimum, with jitter), otherwise back off with jitter; `429` `slow_down` also reduces the request rate and ramps it back; quota, billing and spend-limit errors are not retryable; a server delay above the client's maximum defers the request and never retries sooner. Codex (`openai/codex` `a0a30c40`, `core/src/responses_retry.rs`, `protocol/src/error.rs`, `async-utils/src/backoff.rs`): a failure to connect retries without limit (5 s doubling to 60 s, feature `unbounded_connection_retries`, on by default, no connectivity probe); other transient errors get 5 stream retries (200 ms doubling, ±10% jitter, `Retry-After` overrides); `server_is_overloaded` is retried only when `Retry-After` is present, otherwise it is surfaced as "try a different model"; plan usage limits, quota, spend limits and auth are never retried.
    - Retention by class. Overload (Anthropic `529`, OpenAI `503` `server_is_overloaded`): if `Retry-After` fits the head window, wait and retry the same route, otherwise fail over for this request only (policy permitting); the route is eligible again after a cooldown of max(`Retry-After`, backoff), backoff 5 s doubling to 60 s with jitter, reset on success; three overloads of one route within a job keep it out for the rest of that job. Rate limited (`429`, including `slow_down`): out until `Retry-After` or the observed reset; `slow_down` briefly lowers that route's admission rate. Subscription quota exhausted: out until the observed reset (unchanged). API credit, spend limit, authorization: out for the job (unchanged).
    - Network (transport class: never a refusal, never marks a route, never fails over). Part A: a connect failure before any request byte (DNS, TCP, TLS) is held in the request and retried (5 s doubling to 60 s) while the container's head window allows, the container seeing nothing; offline is detected when every route fails at transport, confirmed by a cheap probe (name resolution and TCP connections to two unrelated hosts, plus the OS default-route or network-manager state where available), probed again immediately after a wall-clock jump (wake); a drop after request bytes keeps the attempt `Uncertain` and retries as a new journaled attempt at most 5 times; online with one provider unreachable is a provider outage under the normal failover policy. Part B (with slice 4): a longer outage pauses the job with resume trigger "connectivity restored", waits without limit (offline spends nothing; the operator can stop it), shows "waiting for network since T" and notifies once.
    - Gates (part A): an overload with an in-window `Retry-After` retries the same route and reaches the container as one response; an overload without it fails over for that request and the next request returns to the route after its cooldown; the third overload in a job keeps the route out; `slow_down` lowers the route's admission rate; quota, credit and authorization retention unchanged; a connect failure is never a refusal or a failover and is retried inside the head window; all-routes transport failure plus a failed probe is recorded as offline, not as provider state; a mid-stream drop stays `Uncertain` and is retried at most 5 times; every retry and cooldown is journaled and `recover`/`replay` reproduce the decisions.
