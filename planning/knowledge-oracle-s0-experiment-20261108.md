## 1. Questions

S0 tests register questions Q18 and Q17 for one model on one host. Q18 asks
whether models consume exact claims correctly and whether that improves
outcomes; S0 covers it without context replacement, which is in S0b. Q17 asks
whether an arm handles a change in evidence correctly. That means noticing it,
without treating it either as harmless or as proof the conclusion is false.

S0 reports two benefits separately:

- **Receiving** curated knowledge: arm C against arms A and B.
- **Recognizing** a need and asking for it: arm B on embedded items, scored on
  steps r1–r4.

Recognizing needs is the decision-aware path's responsibility. S0 measures
only the unaided baseline for it (boundary note, section 4).

**No-write controls:**

- **N-1.** Both stores are read through copies made at U-1, with the originals'
  revisions and digests recorded. If U-1 finds that a read profile cannot open
  a copy, the original is read in place, and SC-9 integrity checks apply to it.
- **N-2.** Arms have no Bash, Edit, Write or notebook tools. Their only
  connections to the stores are the claims read tools, whose callers cannot
  publish, record reliance, choose authority or change scope. No producer
  startup, bootstrap file or claims-host executable is reachable through any
  arm tool.
- **N-3.** The W1 read profile is a configuration file in the S0 work
  directory. It differs from the store's read profile only in its evidence
  checkout (W1). It changes no store, bootstrap, config or source file.
- **N-4.** The root writes only under `~/cbm-work/oracle-s0-<date>/` and in the
  two worktrees. It does not write to the main working tree, the register or
  any store.
- Codebase Memory indexes W0 and W1 at U-1. That writes only to Codebase
  Memory's own store.

**Isolation**, verified at U-2 and checked after every run:

- No auto-memory loads, because the worktrees are outside the main project
  directory. The memory notes contain corpus facts.
- The answer key, the curator's projections, and sealed run outputs are outside
  every arm's allowed read paths, enforced by deny rules. A U-2 smoke run
  attempts such a read and must be refused.
- Arm A has no claims tools or register view.

## 3. Items

There are 12 items in total.

| Kind | Count | Categories (parent design, section 12.2) |
|---|---|---|
| Explicit | 8 | one each of categories 1–8 |
| Embedded | 4 | one each drawn from categories 1, 4, 5 and 6 |

**Embedded items are tied to register decisions.** Each embedded item is a
task bearing on one of the register's 11 decision records, identified by
`decision_id` and exact `revision`, whenever a suitable decision exists. Where
none does, the decision identity is recorded as `not established`. This uses
the decision-identity contract proposed in the boundary note, so the
decision-aware investigation can reuse the items and the key.

**Changed-source items.** There are two: the category 6 explicit item and the
category 6 embedded item. Each rests on a source anchored by a captured claim,
and W1 changes that source.

- One change preserves meaning: the bytes change but the conclusion still
  holds, for example a nearby comment or reordering.
- The other change alters meaning, so the conclusion no longer holds.

The item author decides which is which and seals that record. The key preparer
is not told, and determines the conclusion status independently by reading the
changed source.

**Sample size.** n = 12 per arm, n = 1 per category cell for explicit items,
and n = 4 for the recognition measure. Results by category are anecdotal.

Eight items give an arm the chance to reuse something falsely: explicit items
in categories 4–8 and embedded items in categories 4–6. Both changed-source
items are among them.

## 4. Arms and runner

- **Model and effort**, all arms: `claude-sonnet-5-5` at `medium`, following the
  Claude reconnaissance row in `docs/model-selection.md`.
- **Arms:**
  - **A:** W0 or W1; Read, Grep and Glob; Codebase Memory.
  - **B:** A's tools plus the claims read tools for both store copies and the
    register view file.
  - **C:** B's tools plus the curator's projection for the item, attached to the
    task.
- **Runner.** One headless Claude Code process per run.
  - Each arm has a settings file fixing the model, effort, tool allowlist, MCP
    servers and deny rules.
  - Each run has its own transcript, so the usage ledger can attribute its cost.
  - The runner writes each run's output to a **sealed directory** and records a
    digest manifest.
- **Order.** Runs are put in randomized order. Assignment and exposure are
  recorded, through `experiment-control` if U-2 confirms it fits.

## 5. Roles and the independent answer key

Each role is a fresh session that sees only what is listed for it.

| Role | Model | Sees | Produces |
|---|---|---|---|
| Item author | Opus 5.5 high | corpus, parent design section 12, register decisions | 12 items: text, category, need statement, decision identity, target pointer, and the sealed record of which change preserves meaning |
| Key preparer | Opus 5.5 high | item text and corpus, including W1. Not the author's pointers, notes or sealed record. | the per-item key fields below |
| Second key reader | Sonnet 5.5 high. Astra is a separately authorized option (section 8.4). | item text, the key and its sources | agree or disagree per field, with reasons |
| Curator, arm C only | Opus 5.5 high | item text and readers. Not the key. | 12 projections in the parent design's section 9 format |
| Scorer (stage 2) | Opus 5.5 high, not the key preparer | frozen key; outputs and tool-call logs with arm labels and attachments removed | per-run scores (section 6) |
| Second scorer (stage 2) | Sonnet 5.5 high | the same, for a random 9 of the 36 runs | agreement check |
| Root | Opus 5.5 | setup and gate data | setup, runs, checkpoint report. It must not edit the frozen key or open sealed outputs. |

**Key fields per item.** Evidence status and conclusion status are separate
fields, each with exact sources:

- **Evidence status.** These are facts read from the owners:
  - per-anchor currency (`bytes_match`, `bytes_changed`, `unavailable`);
  - whether the cited revision is current, and which successor exists;
  - owner-recorded register events (correction, challenge, status
    discrepancy).
- **Conclusion status.** This is the key preparer's judgment from reading the
  sources, checked by the second reader. One of:
  - `supported`;
  - `no_longer_supported`;
  - `not_established`;
  - `applies_to_other_environment_only`;
  - `corrected_by_owner`, only where an owner's register event or successor
    revision records it.
- **Correct answer**, and what counts for this item as false confident reuse
  and as false invalidation.

A byte change, or the existence of a successor revision, sets evidence status
only. It never sets conclusion status by itself. The key records conclusion
status from reading what the changed or successor material says.

**The key is frozen before any arm runs.**

1. A script compares the preparer's sources with the author's pointers, and
   the preparer's conclusion status on changed-source items with the sealed
   record.
2. Disagreements go to the user to adjudicate, rewrite or drop.
3. The frozen key's sha256 is recorded.

Neither the arms nor the curator ever see the key.

All roles except an optional Astra reader are one model family. Their errors
may be correlated, and the report states this.

## 6. Scoring and measures (stage 2)

**Per run:**

- **resolution:** correct or incorrect against the key;
- **false confident reuse:** stating or acting on a conclusion as current,
  supported or applicable when its conclusion status is
  `no_longer_supported`, `not_established`, `applies_to_other_environment_only`
  or `corrected_by_owner`;
- **false invalidation:** treating changed evidence, a successor's existence,
  or an event on a different finding as proof that a conclusion is false or
  inapplicable, when its conclusion status is `supported`. This is a separate
  error class, never merged into false confident reuse;
- **unnoticed evidence change:** on changed-source items, whether the run
  registered the change at all. A run can be right about the conclusion while
  missing the change, and that is recorded rather than credited;
- **provenance accuracy;**
- **r1–r4** on embedded items in arm B, with arm A's r1 as the baseline.

**Reporting.** Every false-confident-reuse occurrence is listed individually:
item, category, arm, what the run asserted, the key's evidence status and
conclusion status, and a transcript reference. Changed-source and
not-established cases are listed first. False invalidations are listed the
same way.

**Totals per arm:** false confident reuse over the 8 items that allow it;
false invalidations; total inference cost per correctly resolved item (for
arm C including the curator's cost; key and scoring costs reported
separately; an unattributable cost is reported as unavailable, never as zero);
missed reuse; latency; and context tokens added.

**Routing benchmark** (stage 2, no agents), on the 12 item texts:

- substring `discover`: deterministic, no model cost;
- one Sonnet 5.5 medium call per item, choosing among host-supplied candidates;
- abstain-always.

Measured: correct route, false route, missed route and correct abstention.

**Scorer agreement** is reported on the 9 double-scored runs.

## 7. Decision rule

These thresholds are frozen by the user before stage 2 is authorized. The
values shown are the user's corrections where given, and proposed defaults
otherwise.

- **Safety, required to proceed to S1.** The arm's false-confident-reuse count
  must not exceed arm A's: no increase is allowed. Per the user's correction,
  this has no margin.
- **Cost, required to proceed to S1.** The same arm (B or C) has lower total
  inference cost per correct item than arm A.
- **Proceed to S1** only if arm B or C meets both conditions. Even then the
  result is a feasibility signal, not qualification.
- **False invalidation.** Reported per occurrence. It does not gate, unless the
  user chooses to freeze a threshold for it.
- **Routing passes for S2** (proposed default): the model router's false routes
  are 1 of 12 or fewer, and it makes more correct routes than substring
  `discover`.
- **Stop** if neither B nor C meets both conditions. The result is recorded
  through the register owner under Q17 and Q18.

**Interpretations.** These are reported with their counts and do not gate.
They follow the boundary note's assignment of responsibilities:

- C beats A, but B does not, because r1 or r2 is low: there is a recognition
  gap. That is an input to the decision-aware path, not a reason to widen the
  oracle's scope.
- r1 and r2 high but r3 low: there is a resolution or routing gap. That bears
  on oracle stage S2.
- B about equal to C: projections add little over raw reads.

### 8.3 Checkpoint: setup and budget only

**The report contains:**

- spend by line, against the stage 1 forecast;
- the pooled per-run cost of the valid pilot runs (mean and maximum across all
  arms, never broken down by arm);
- pass or fail, with evidence, for U-1 to U-3 and for each pilot run's isolation
  and no-write checks;
- integrity: store revisions and digests, register files, and the original
  disposable store, all unchanged;
- completeness of cost attribution;
- the frozen key's digest, and how many items were adjudicated, rewritten or
  dropped (SC-1);
- the stage 2 projection and the requested stage 2 cap.

**The report excludes:**

- pilot outputs and any scores;
- per-arm costs, token counts or tool-use counts beyond pass or fail;
- any comparison between arms.

Pilot outputs stay sealed until stage 2 scoring. If S0 ends at the checkpoint,
they stay sealed and unscored, and scoring them needs a separate decision. The
root's transcript is checked for any read of the sealed directory. A read is a
protocol deviation and is reported (SC-11).

**Stage 2 projection.** This is the requested stage 2 cap, rounded up to whole
dollars:

```text
P2 = 18 x max(m, 0.35)          explicit runs; m = pooled mean of the valid pilot runs
   + 12 x max(0.85, m)          embedded runs: never priced below the conservative 0.85
   + 2.40 + 3.50 + 0.85         routing, scorer and second scorer at forecast high
   + 8.00                       stage 2 root at forecast high
```

The pilot's mean can raise the embedded price but never lower it, and support
roles that have not run stay at their high forecasts. With m ≤ 0.35, P2 is
31.25. Each $0.10 that m rises above 0.35 adds $1.80 while m ≤ 0.85.
