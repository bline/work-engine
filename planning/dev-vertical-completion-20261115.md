## Boundary and ownership

```text
execution contract / operator constraints / applicable policy
                         |
Pi container -- inherited framed IPC --> trusted Rust host inference boundary
                                         | candidate selection
                                         | funding admission
                                         | credentials + transport
                                         | attempt observations
                                         v
                              authorized provider connection
```

The gateway is the execution boundary within an inference efficiency router.
Selection, funding, and dispatch are distinct responsibilities; they need not
be separate services or three new crates.

| Responsibility | Owner or placement recommendation |
| --- | --- |
| Work, model/capability constraints, review requirements, permitted alternatives | Existing execution/admission contract; later compiled policy projects those decisions |
| Candidate ranking, effort/cache tradeoffs | Bounded routing policy initially; qualified optimization can extend it |
| Permitted funding routes, reservations, limits, uncertainty | Existing admission/accounting owners composed at the host |
| Credential custody, account identity, refresh, upstream authentication | Existing host credential owner and provider adapter |
| Pi session, tool execution, workspace, checked export | Native Pi/manual-host and existing retention/lifecycle owners |
| Dispatch and raw/normalized attempt observations | Host transport; existing financial owner interprets financial meaning |
| Research qualification and applicability | Research owner, outside the router |

Start in the existing Rust host/library composition, reusing
`bounded-inference` mechanics and Pi's IPC ingress. The initial placement task
is to identify the narrow reusable request/stream interfaces across Pi and
Direct, including their incompatible profiles. A new daemon, generic HTTP
proxy, universal provider protocol, or second ledger is not justified by the
current evidence. This is an architectural recommendation, not an exact-route
acceptance requirement. Rust remains the first-party implementation direction;
the small SDK-facing Node receiver remains an adapter to third-party Pi.

## Delivery sequence

The sequence below is a practical default. Its phase exits describe evidence
and outcomes; it does not replace the owning acceptance contracts.

### 1. Establish the integrated target and reconcile inherited qualification

Recover the paused state, source/binary/image pins, findings, and budget/authority
owners. Describe the supported coding request and streaming result, the selected
route pair, and the shared host interfaces. Reconcile the operator-approved
unchecked temporary scratch boundary with checks before Work Engine retention,
export, and custody publication. Keep the old FT-01 counterexample as history;
the approval changed its applicability, not its observed result.

Exit: a bounded implementation slice and updated qualification mapping, with
all original classes retained and any changed acceptance owned explicitly.
No renewed campaign allowance is inferred from the former $70 envelope or the
approximately $13 allocated to this preparation.

### 2. Prove one complete streamed coding request through the host

Extend the existing Pi IPC transport to deliver headers, bounded body chunks,
completion/failure, cancellation, and backpressure incrementally. Preserve Pi's
native provider parser, tool calls/results, and continuing session. The host
validates the admitted request, reconstructs the allowed upstream destination,
and obtains credentials without handing provider secrets to Pi.

Use one synthetic route first. Generalize the narrow tool-free host profile
only where the actual coding request requires it; request construction and
response/tool observation both need coverage. Persist admission/reservation and
send intent before possible provider entry. Preserve raw screened evidence and
normalized usage, including cache fields and missing values, from this exact
transport. Secret-bearing captures stay under the existing protected custody
rules rather than becoming ordinary job exports.

Exit: actual native Pi consumes an early response chunk while the endpoint is
still open, completes a tool round trip and second inference request, then
exports checked evidence. Slow-reader, bounded-buffer, cancel, malformed-frame,
and interrupted-stream controls exercise the real bridge. A body containing
SSE text delivered only after EOF is not a passing streaming control.

### 3. Add bounded route selection and failover

Begin with explicit operator-selected model/effort and authorized connections.
A pinned policy can rank those candidates and enforce funding preferences,
finite attempts, per-source limits, and the overall allowance. Mechanical
admission is deterministic; determining adequate task quality remains with
the model or an applicable qualified policy. Unknown availability stays unknown.

Exercise two synthetic funding routes. A definitive eligible failure can cause
a new admitted attempt under the configured policy. An interrupted or partly
adopted stream returns an explicit uncertain outcome to the continuation owner;
the first version need not splice responses or automatically replay it. A quota
error arriving after streaming begins needs its own failure-path control.

Each switch retains its predecessor, reason, actual connection/model/payer,
configuration, policy/observation revisions, reservation, and available usage.
An unresolved charge keeps its conservative obligation; financial settlement
is not inferred from HTTP completion. An unknown tool effect cannot become
permission to execute that tool again. Stop or return a structured unavailable
result when no permitted route exists. Subscription preference alone never
grants paid fallback, and billing fallback never grants model substitution.

Exit: successful authorized fallback plus refusal of unauthorized, incompatible,
over-budget, stale/revoked, and uncertain switches; restart during a switch
preserves one task/effect history and all inference attempts. Stable routing
avoids needless switches; cache savings remain unestablished until measured.

### 4. Compose the development path and expose lane interfaces

Wire the router into the actual development-host composition, replacing the
old credential-mount execution behavior for the selected profile. Run it
offline before enabling any live route. Preserve lifecycle authority, checked
snapshots, useful scratch tools, result interpretation, and sealed recovery.
Internal consumers may change together; no dual-running compatibility bridge
is required merely to preserve the old implementation.

Exit: one joined offline job performs real code creation, build/tests, evolving
native snapshots, checked export, disposal, and fresh sealed read/reconciliation
through the selected host path. Source, executable, SDK/image, policy, attempt,
observer, and artifact identities join on that same subject.

### 5. Close failure qualification, regression, and exact-subject review

Complete the missing crash/capture-failure/journal-loss/observer-loss/partial-frame
and repeated authenticated reconciliation controls. Keep lost-ack, late-response,
and unknown-effect evidence. Re-run affected end-to-end evidence after material
changes; source12's successful workflow predates FT-02 and later integration.

Obtain the required broad regression result. The four Claude ProgramDrift
failures and intermittent owner/host failures need bounded baseline attribution
and repair or an owner-approved disposition; isolated passing reruns do not
turn the original broad run green. A plan does not waive a test.

The inherited exact-source/proof review explicitly names **Astra/xhigh**.
Claude implementation or a Claude self-check cannot close that gate. Use the
configured reviewer when available, or obtain the acceptance owner's explicit
change to that reviewer contract while preserving its required independence.
Retain useful review context through remediation under the governing contract.

Exit: all applicable offline acceptance predicates and the required whole-subject
review are established; historical findings have truthful dispositions.

### 6. Qualify real routes and operational cutover

Prepare the concrete live request, credential custody, selected accounts/models,
funding caps, evidence/closure basis, and rollback before seeking the missing
live authority. Then qualify each real route separately and the permitted
transition between them. The offline profile and synthetic issuer do not prove
real registration eligibility, permissions, tool support, or funding behavior.

The public OpenAI Responses path is a promising first candidate because of the
existing host work. It requires its actual registration/permission and account
model checks; redirecting the legacy Pi Codex transport or reusing its token
without qualification is insufficient. The current documentation specifies
`store:false` and `stream:true` for that plan-usage flow.
See [models/inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)
and [registration/sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Preserve scoped failure observations: OpenAI says its plan-usage-limit error can
reflect an app-specific limit and does not establish total-plan exhaustion or
reset time. See [errors/recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

Exit: an authorized real development job and compatible real funding transition
have joined evidence, remaining financial/custody obligations stay with their
owners, final acceptance covers the exact integrated subject and evidence, and
the approved operational entrypoint uses the qualified path. Local completion
alone does not establish remote or financial settlement. Push/deploy/cutover
authority remains with its existing owner.

## Which ideas help now, and where other lanes join

| Idea or lane | Use in this completion path | Later expansion |
| --- | --- | --- |
| Host gateway/native IPC | Central execution boundary now | Remote gateway only when an actual deployment needs it |
| Resource management | Explicit funding preferences, limits, failure reasons, and permitted fallback now | Live adapters/availability for all four funding streams |
| Usage/attempt accounting | Common attributable observations now; retain unknowns and separate cost bases | Production-qualified financial reducer integration |
| Cache affinity/effort | Collect actual cache evidence now; keep configuration stable | Controlled warm-prefix/effort/route experiments and qualified switching policy |
| Plan IR/organizational compiler | Consume admitted constraints and stable policy identity at the host | Compiler-produced inference policy when its lane is accepted |
| Research | Observation export and a policy-applicability input seam | Qualified quality/cost/latency findings changing eligible policy |
| Review/lifecycle | Actual provider/configuration identity, cancellation, no duplicate effects now | Additional workloads through the same bounded interface |
| UI/connections | Stable nonsecret connection/route metadata and structured failures | Named-connection management and selection UI |

These seams should let lane owners integrate without giving the router their
authority or making completion wait for every adjacent campaign. The standalone
[attempt-accounting pilot](../experiments/pi-attempt-accounting/README.md) remains
experimental with financial qualification/reviews open; it is not an accepted
production ledger simply because the gateway can emit its inputs.

The immediate next slice is phase 1 plus the smallest phase-2 implementation
that proves incremental Pi coding traffic through a single host-owned synthetic
route. It resolves the largest integration uncertainty before adding route
selection, optimizer sophistication, or broad new provider support.
