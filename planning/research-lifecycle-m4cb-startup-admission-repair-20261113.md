## 1. Repair decision

Replace the pre-launch native-PID requirement with a lifecycle-owned, two-phase native startup handoff. First validate and retain every installation/authorization record without mutation. Then let the existing lifecycle owner create its actual native child, initialize its non-inference protocol and hold it before any model turn. Observe that owned realization, join it to the exact approved startup and current trusted host, install the scoped research consequence, and release the same held realization. Missing or mismatched evidence causes refusal and owned cleanup; it cannot release the child or supply a producer.

This requires a narrow amendment to `lifecycle-codex` and `lifecycle-service`, in addition to the host/task/research paths in the former host-only scope. The former premise that a host-only input file could bind the subsequently created native child is false. The root's `O1-COMPOSITION-DISPOSITION.md` still supplies the settled conditional authentication boundary; `HOST-COMPOSITION-REFINEMENT.md` supplies no authority to preserve its disproven host-only placement. This plan proposes the new placement for review. No code or component contract is changed here.

For installed v3 restart, compare unchanged semantic settings and prove a bounded replacement of realization/admission records. Independently require the complete new upstream configuration C to equal the current S projection. Never suppress differing C/O pins merely to pass equality, or retain old C to avoid refreshing its dependents.

Keep the selected native access-lease realization and pinned isolation profile. No new executor, general observer service, public installer RPC, inference grant or producer-supported final-model-input hook is introduced. C1 remains unavailable; production fresh prepare/adopt must still refuse.

The dedicated trusted composition constructs it only under the existing O1 caller contract. It contains the current host identity acquired by the host, not an input claim about a future host or native process. Hashes, files, UID, a flag or a JSON boolean cannot establish authentication.
3. **`AdmittedResearchStartup`**, host-private, adds a current lifecycle-owned realization and admissible protection observation after that realization exists. Only this consequence can enable installed producers. It retains the actual selection/S/I/C/O/admission/source/host/native association.

### 4.2 Cold startup sequence and failure boundaries

1. Trusted selected preparation obtains exact selection/S and fully checked records plus the conditional operator authorization (§3). There is no native PID to supply yet. Complete all deterministic refusals before effects.
2. Under existing startup/store ownership, create/open stores and publish existing startup intent/receipt as appropriate. Such a receipt identifies selected store custody; it does **not** assert active research admission. Keep its historical format/meaning.
3. Start the existing lifecycle service with an installed-startup hold. Actor creates the one native runner; the runner spawns its one actual child using current isolation. No separate host child is created. The service may serve its bounded internal initialization/readback/shutdown paths; it cannot admit productive task/native work during the hold.
4. Runner initializes and validates effective policy/provider/auth and starts/binds its thread through existing owned protocol. Place the hold before the earliest `run_turn`, including successor rehydration, before `PrepareTurn` and before any `turn/start`. Early native tool/server requests cannot invoke task effects or be replayed past admission; reject/quarantine them under existing bounded ingress rather than treating them as authorized work.
5. From the held harness obtain the new actual-child observation and complete configuration/tool evidence. Lifecycle sends exactly one `PendingNativeStartup` to this host. Host compares current host, selection/S/native configuration, protected roots/bytes, upstream I/C/O/admissions and qualified observation source. Decoy PID, old ticket, unrelated transport or missing observation refuses.
6. Construct the private admitted consequence, then install the checked exact role/key scope. Nomination/key setup remains one task-owner transaction; no producer is exposed before it. Persist notice/admission associations only with their existing domain outcomes. Do not manufacture a notice as a startup marker.
7. Recheck the same pending realization and activate it once. Only then expose the host's productive request service and permit lifecycle native turn entry. Activation cannot change the selected child, thread/transport/incarnation, startup bytes or protected roots. Currentness failure revokes the pending/admitted consequence and invokes existing cleanup.

Task-owner setup and lifecycle activation are separate owner transitions, not a cross-store atomic transaction. If activation fails after nomination/key setup, retain that truthful setup and refuse service; do not claim an active installation or roll back unrelated state. Retrying this exact stopped attempt follows existing selected/restart and owner CAS rules; it never synthesizes a fresh grant, recreates a turn or uses a stale activation ticket. Process loss after activation makes fresh producer use unavailable. Exact historical receipt readback remains possible under the existing recovery route without asserting a current admission.

Failure/drop/shutdown at every hold boundary must close activation, prevent all model entry, terminate and reap through lifecycle's existing owner and retain unsafe/unknown cleanup classifications. Initialization can consume the already-required access authentication exchange but authorizes no inference. Future local qualification must use provider-disabled credentials/transport fixtures; no real access lease is authorized by this plan.

## 5. Lawful installed v3 restart

The supported repair is an installed-to-installed restart under the **same upstream authority and semantic configuration**, with a newly authorized realization and refreshed downstream records. It does not broaden v2 reselection or add an installed/uninstalled transition.

Retain and verify predecessor selection/S, receipt, store stamps and exact restart declaration. Preserve cooperative predecessor-stop/exclusion, native epoch CAS, task owner/revisions, context/snapshot/profile/binary/protocol and saved-command fences already owned by selected startup and lifecycle. Existing exact-observation receipt completion is readback/recovery, not authority to relaunch a duplicate process.

Form the successor acyclically:

`I/R_I unchanged → complete new C2 → O2 → actual R_O2 → S2/selection2 → actual new realization/admission evidence`.

New C is required because full S's upstream portion includes the new native root/session/invocation/attempt identities. O2 binds C2 and the same complete finite intents. Give changed records fresh immutable member names and any changed manifest locator a fresh ID; retain predecessor bytes. Obtain actual approval of O2 and the completed S2/selection2 through O1. A predecessor approval of O1/S1 is not approval of their replacements. Actual current host/native/protection evidence is acquired after spawning the successor, as in §4.

Produce a private `ValidatedInstalledRestartReplacement` during the pure preparation phase. Its proof has three parts:

| Comparison | Required equality / permitted difference |
| --- | --- |
| Complete semantic startup | Compare the entire typed predecessor and successor S after replacing **only** the four already permitted native fields (`session_id`, `root`, `invocation_id`, `attempt_id`) and the exact installation-selection fields justified below. All other present/future fields compare by default. Preserve changed control/provider/source/auth/isolation/helper/proxy/profile/snapshot/grants/prompt/research nomination/selectors/roots as mismatches. Same-parent fresh private native root and distinct session remain required. |
| Installation replacement | Same protected installation root, version, I and R_I exact bytes/pins and authority/key/purpose/roles/selectors. Only configuration, operations and operation-admission member pins may be replaced. Validate predecessor records against S1 and successor records against S2 separately. O2's complete role/key/kind/payload intent set equals O1's, with only its configuration link and fresh record locator differing. R_O2 is newly authenticated authorization of exactly O2 under unchanged I; different admission/source/caller bytes are admissible only through that proven approval, never ignored because their keys have certain names. |
| Independent full current configuration | Require **all** C2.upstream_startup == upstream(S2), exact I/R_I links, O2.configuration_digest == H(C2), exact R_O2/O2 and S2/selection2 links. This comparison does not use normalized S. Likewise verify predecessor C1/S1 correspondence. Passing semantic equality cannot waive this current comparison. |

Only after that proof may `compatible_restart` normalize the specific changed selection pin values for semantic comparison. Do not clear the entire `research` or `installation` object, ignore arbitrary JSON fields, compare only known security labels or use a normalized hash as the current configuration digest. Installed/uninstalled transitions, altered I/R_I/root or changed intents require their own approved semantics/installation route; they are outside this repair.

Old B/preparation/adoption data, receipts, immutable task input and saved lifecycle commands continue to name their original I/C and outcomes. A B bound to C1 does **not** become current under C2 by normalization or by editing its configuration digest. Future fresh preparation/adoption would need a genuinely current checked B2 and all upstream recommendation/delivery requirements; C1 remains unavailable here, so those production calls still refuse. Notice-only intents remain independent of B and can run after this bounded authorized restart. Historical exact retries return the original receipt and original admission association; a new fresh notice records the successor association atomically with its outcome.
