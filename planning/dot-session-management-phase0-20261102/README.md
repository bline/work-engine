# Dot session management: phase 0 result

Phase 0 reconciles the two existing sessions' contracts, source placement and
reuse. It produces a concrete next bid; it implements or activates no runtime
behavior. The user's approval of the [completion plan](../dot-session-management-completion-20261102.md)
admits only this plan's recommended **$10 / 75 minute phase 0**, across both
sessions. Phases 1–6 and the full planning envelope are not funded by it.

The joint boundary is one existing signed decision source, one protected Rust
task/admission owner, canonical accounting and one native custody owner. Keep
owner-answer/v1 bytes and the existing bridge's RPC meaning. The current generic
approval view needs typed execution terms before writable work. A task consumer
must reconcile a request closed by its own exact verified answer rather than
confusing it with withdrawal or replay. That consumption-rule refinement is a
proposal for the next implementation approval, not a changed live policy.

No model actors, native task, provider credential/configuration, service,
deployment or skill activation was created or changed under phase 0. Existing
OAuth verification and bookkeeping work retain their separate owners and
allowances. The merged bookkeeping candidate is useful supported reuse, not a
second product dispatcher or automatic global activation.

The first implementation slice is deliberately bounded: typed review, exact
decision verification, durable one-answer admission, canonical capacity,
one isolated Codex write profile and an exact result/cost/custody projection.
Claude, Away, general steering/concurrency and production workspaces remain
later slices. The real Dot authenticated-read prerequisite remains separately
unestablished. A live writable pilot requires a concrete qualified packet and
the owner's exact signed task after implementation review.
