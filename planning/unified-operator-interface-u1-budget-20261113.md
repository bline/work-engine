## Architectural blindness protection

Repeated repair failure can falsify the plan, ownership boundary or architecture.
Treating every rejection as another local coding mistake can hide that evidence
and spend the budget without producing a valid result. The following exact
triggers are the user's operating contract for this work; they are not a claim
that a failure count proves a particular redesign is correct.

| Signal | Required response |
| --- | --- |
| First independent technical rejection with serious defects | Record an architectural-risk warning, its boundary and evidence. Permit a bounded repair if no immediate escalation condition applies. |
| Second rejection after a repair within the same subsystem | Block another ordinary repair cycle and require an Astra `xhigh` architectural/design review. |
| Confirmed serious regression caused by a repair, or recurrence of the same invariant violation | Escalate immediately to the same design review, regardless of rejection count. |

Here, serious technical defects mean P1 or P2 under the review contract: P1
blocks acceptance; P2 must be fixed before acceptance; P3 is an improvement.
Record the actual evidence, not only a verdict string. A technical rejection
is one independently reviewed submitted subject that has a supported serious
defect. Multiple findings or duplicate delivery of the same report do not
multiply that rejection. A later rejected repaired subject is a new event.
Retained review can remain independent of building; changing reviewers is not
required merely to count a new technical result.

Track evidence by the affected subsystem and architectural boundary/invariant,
with exact submitted subject, report, repair lineage and owner. Worker, reviewer,
slice, budget or file renaming does not erase that history. When a finding spans
boundaries, record the affected boundaries rather than selecting a convenient
new bucket. A confirmed recurrence means a distinct exercised state or subject,
not a replayed notification of the original defect.

**Inherited defects count.** Preserve whether each finding was introduced,
inherited or unresolved, but do not use that label to exclude a technical
rejection or repeated boundary failure from the escalation evidence. Repeated
exposure of an inherited boundary defect can trigger review even when the
current repair did not introduce it. Preserve outside-owner findings as design
evidence without silently expanding mutation authority.

Infrastructure interruptions—including Flex capacity errors, reviewer budget
exhaustion, transport interruption or an incomplete review—do not themselves
count as implementation rejections and do not reset accumulated evidence.
Preserve substantive findings from a partial report for assessment: an
independently supported serious regression or recurring invariant still
escalates. Uncertain classification stays visible; it cannot be relabelled
infrastructure to bypass an unresolved technical gate.

The supervisor evaluates these signals on each review, repair and qualification
result, before admitting another repair, and on relevant owner updates. It
records the warning or gate and automatically dispatches the required review
when scope, context and budget permit. If dispatch is unavailable, the gate
remains blocked and is reported. This is the supervisor's orchestration
contract, not an installed global hook or a new automatic enforcement service.
Every governed builder and reviewer receives this contract's applicable reason,
triggers and current boundary history with its packet before dependent work.

The escalation reviewer starts apart from builder/designer reasoning and receives
the exact plan, rejected subjects, repair deltas, relevant inherited findings,
validation failures and owner contracts. It asks whether further local repair
is justified or the plan, ownership or architecture needs revision, and identifies
evidence supporting that conclusion and credible alternatives. An ordinary code
recheck does not satisfy this architectural review merely because it used Astra.

Resume only against an explicit review disposition and a bound current plan.
If local repair is justified, record why the architectural risk was addressed.
If redesign is needed, revise the plan and acceptance evidence before another
implementation attempt. Root can approve small changes within existing
authority; large cumulative changes or a changed owner/user boundary require
the owning authority. A design review neither grants extra budget nor accepts
the product. Preserve earlier rejection history and the reviewer disposition;
do not silently reset the ledger after a warning or a successful local test.
