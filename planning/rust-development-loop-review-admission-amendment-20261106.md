# Development loop: review-admission seam amendment

Recorded 2026-11-06 UTC. **Proposed; not implementation authority.**
Parent: [approved loop scope](rust-development-loop-closure-budget-20261106.md).
Evidence: [first checkpoint](../records/rust-development-loop-feasibility-20261106/README.md).

## Why the first checkpoint holds

The supported Rust qualified-review path uses Claude and a protected deployment
acceptance bound to an exact historical candidate/session/attempt. There is no
established unprivileged private-job admission route for a fresh real review in
that inspected profile. Offline authority is a different capability. Selecting
the existing Claude reviewer is allowed by the approved objective; the earlier
Astra restriction was a packet error, not a human model requirement.

The next missing boundary is fresh job-scoped review admission. Treating fixture
or externally written review text as qualified owner evidence would conceal it.
Changing protected installed policy would exceed the original private-local
execution scope. The parent plan explicitly requires a stop and rebid when the
review/authority join needs a broader contract.

## Recommended next deliverable

Prepare and implement the smallest explicit fresh-job review-admission seam in
the existing Rust admission owner, using the existing qualified Claude execution,
custody and evidence consumers. Establish a reviewed contract separating trusted
installed policy from exact per-job admission. A job request cannot install its
own policy or manufacture acceptance. Preserve the current fixed-profile route
and historical records.

Before implementation, settle whether the existing deployment owner can issue a
fresh exact admission through a bounded supported callable, or whether the Rust
owner needs an additive profile/API. Prefer reusing that owner over a second
grant store. Do not expand this into a generic provider, identity or workflow
platform. If a safe bounded seam cannot be specified inside this deliverable,
return that concrete contract limitation rather than add another backend.

Acceptance of this deliverable means an actual Rust owner/API can admit a fresh
candidate under explicitly installed test policy, persist/reopen the exact
admission and feed the existing execution consumer. Tests must refuse changed
candidate, session/attempt, stale/revoked or wrong policy, replayed entry and
caller-supplied authority. Fixtures must remain explicitly fixtures. Preserve
one-shot entry and uncertain effects; reopening cannot mint replacement execution.

Separate review covers authority, state and replay semantics. Produce a private
source checkpoint, focused qualification and exact operator/deployment handoff.
No `/etc` changes, privileged installation, live provider calls or production
activation occur in this amended deliverable. The later live proof needs its
fresh exact authority and explicit operator acceptance/publication decisions.
