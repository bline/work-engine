# Claude subscription support for Python Pi containers

**Status:** Proposed implementation plan; core scope reviewed and remediated. Scope is the Python `role_host.py` / `pi_container.py` path. This record does not authorize implementation, install, live credentials, model calls for qualification, or rollout. See [review and budget basis](#agent-time-and-api-equivalent-budget).

## Outcome and boundary

Support `role_host.py launch pi --container --auth subscription --host-arg=--model --host-arg=claude-sdk/<exact-id>` and `deliver` on the same Pi session. Pi still owns its turn and local tools; the Claude Agent SDK starts its Claude Code subprocess **inside** the turn container. The container stays networkless and sees no real provider credential. The host decides whether to forward each model request. Preserve the existing Pi workspace mount, lifecycle, and host-only evidence boundaries. The first supported model is the previously exercised `claude-haiku-5-5`; additional model IDs require their own catalog and exact response-identity evidence. No default provider change, API-key or extra-usage fallback, image rewrite, new grant system, or parity claim with the Rust Host.

The [Rust Host probe](../records/dev-vertical-h2-route-20261117/pi-claude-probe/README.md) established that Claude Code can use loopback with dummy credentials and a host-injected OAuth token. The [Rust Host qualification](../records/dev-vertical-h2-route-20261117/README.md#thinking-blocks-accepted-first-settled-claude-analysis-job-live-c2) completed an analysis job on the subscription path. Those are route precedents, not evidence for this Python runner or for every Pi/SDK/model version. The target Python runner already has the Unix-socket relay ([entry point](../skills/manual-orchestration/scripts/pi_container_entry.py)), Messages SSE parsing and model checking ([proxy](../skills/manual-orchestration/scripts/pi_container.py#L1155)), and a different subscription lane for Codex ([launcher](../skills/manual-orchestration/scripts/role_host.py#L1513)). Extend the existing Python adapter rather than creating a second host or importing Rust Host job semantics. Use the Rust implementation as a reference for the security and billing checks; do not treat its grant or retained-analysis continuity rules as Python session requirements.

**V1 spending semantics.** Require a finite positive `--max-requests` per turn; apply the existing host body and connection limits. Reject `--max-usd`, `--max-output-tokens`, `--usd-strict-tier`, service tiers and API-dollar objective admission for this lane. `--max-requests` is not a session quota or spend cap. A response-header check occurs **after** dispatch; it gates release to the container and supplies provider evidence, but cannot undo a request or independently guarantee that no overage was billed. No automatic API fallback, auxiliary forwarding, or billing estimate in the product's API pool for Claude subscription traffic.

## S0 — Qualify the local SDK wire and freeze the integration contract

**Deliverable:** A repeatable offline probe/fixture and a small, scrubbed wire contract, not a usable live lane. Use a pinned Pi/extension/Agent SDK/Claude Code bundle (including dependency closure), the current container profile and loopback→Unix-socket path, dummy credential only, and a host-local mock Messages upstream. Demonstrate an initial streamed response followed by a tool exchange using a disposable workspace, then a new turn with the same Pi session ID. Capture only fixture inputs and scrubbed wire/evidence, not developer credentials or ambient config.

Pin exact bundle identity, model selection, executable paths, launch/config isolation settings, accepted Claude headers/betas/URL, synthetic auth form, tool and prompt shapes, actual served-model string, terminal/usage shape and retry behavior. Check the Rust precedents against the observed wire instead of copying allowlists blindly. Freeze the host-owned producer/discovery contract for S1/S2: durable turn intent keyed by session/turn; durable request admission and matching disposition keyed by session/turn/attempt; requested and observed model, validated usage and billing-header verdict, with no raw headers, bodies, or bearer. Bind `status` and `usage_ledger.py` to discovery of turn intents even without a successful launch row. Positive no-dispatch evidence, unmatched admissions (possible dispatch/unknown), observed dispatch without trusted completion, and completed usage are distinct; none of the unknown states means zero. Specify how duplicate sources are joined without double-counting. If the pinned SDK needs unapproved auxiliary upstreams, real config or a weaker container boundary, or the mock cannot drive continuation, stop at that concrete blocker; do not widen the route to make the probe pass.

## S1 — Add the isolated Python subscription lane

**Deliverable:** Opt-in launcher plus fail-closed egress, tested through the full Python container path against the mock. Keep live upstream use inactive pending the join and S3 decision.

- Give `claude-sdk` its own subscription selection and provider dispatch in `role_host.py`; do not reuse the Codex credential getter/decoder or the API credential check. Use the same pinned lane on `deliver`. For eventual live use, consume an owner-selected Claude Code credential source on the host only; validate file custody, expected OAuth form and expiry without login, refresh, or inherited key fallback. Refuse host config, credential path/ancestors/aliases and bundle overlaps in user mounts at launch and delivery. Pass the real credential only by the existing private runner handoff, never spec/args/environment. The in-container entry writes only a synthetic, non-authenticating credential in that turn's tmpfs home.
- Explicitly load only the approved provider bundle for this lane and pin its launch inputs. Disable retry/non-streaming/model fallback and nonessential traffic in the SDK; prevent ambient extension, config, or caller overrides from changing this lane's bootstrap. Preserve legitimate Pi tools and caller mounts under the current container profile rather than introducing a parallel tool system. Assert that pinned runtime, mounts and public provider configuration are revalidated on delivery and cannot be shadowed by earlier workspace writes or turn-state edits.
- In `pi_container.py`, reuse the relay, fixed Messages wire and stream parsing where policy matches; keep SDK-specific auth, request policy and billing checks separate from `anthropic`/API. Strictly parse and validate request bytes, then forward the same accepted body. Allow only the observed `/v1/messages` route/query, exact model, streaming and approved client metadata/betas and local tools. Refuse nonzero or missing retry evidence, hosted tools and fallback forms before dispatch; verify SDK prompt/request shape (misconfiguration check, not proof of caller identity). Strip caller auth and reconstruct the bounded upstream header set with the host bearer. Validate the allowed subscription/overage headers and first exact `message_start` model before releasing successful output, and retain unknown disposition when terminal or usage evidence is missing. No redirect, plan-switch or spend fallback. Don't reflect upstream bodies/headers into host logs or relay unsanitized credential-bearing errors.
- Persist a discoverable host-only turn intent (including the expected runner/log/container identities) **before starting a provider-capable process**, and an attempt admission **before any request bytes can go upstream**, independent of all dollar-budget flags. Make file and directory durability explicit on creation, and bind each terminal disposition to its admission. On a failed intent/admission write, do not start/forward; if finalization fails or a process dies after admission, leave the unmatched state discoverable and unknown, never synthesize `not_dispatched`. Use the host-held turn identity and existing cleanup path to reconcile or retire owned leftovers even if the normal launch row was never appended. Do not replay an uncertain request or silently resume through an unresolved turn. Reuse storage mechanics where applicable, not the existing budget policy.
- Verify launch → tool call → resume, selected provider/effort, mount and credential custody, fingerprint drift/refusal, request cap, missing/mismatched billing headers, wrong model, retries, unexpected paths/fields/tools, truncated stream, retire/cleanup and unchanged existing API/Codex lanes. Injection fixtures use synthetic credential markers and assert absence in inspect, container environment/files, argv, spec, status and logs. Add deterministic fault cuts: failed turn-intent persistence before launch, failed attempt-admission persistence before send (mock observes no request), abrupt launcher death after runner start but before the launch row, and abrupt runner death after mock-observed dispatch but before terminal evidence. Produce scrubbed host-only records for S2, including unmatched admissions at those cuts.

## S2 — Account for the route and join the offline evidence

**Deliverable:** `status`, usage ledger and docs expose the new lane accurately; all of S1/S2 is validated together. Consume the frozen S0 event schema in [usage_ledger.py](../metrics/scripts/usage_ledger.py) and add fixtures covering success, refused/no-dispatch, dispatched/incomplete, missing or corrupt logs and duplicate native Pi/SDK transcript entries. Use the host proxy as authority for this container route; retain subscription-lane identity and reported usage separately from `pi_api` and represent gaps explicitly. Do not infer actual quota consumption or invoice dollars from catalog rates. Likewise the `status` handler in `role_host.py` reads host-only records, not the writable container transcript. Document lane selection, supported runtime/model, rejected flags, authorized configuration, usage limitations and qualification status in [Pi host](../skills/manual-orchestration/references/pi-host.md).

After S0, start ledger fixtures/consumer and docs in parallel with S1 in non-conflicting paths. `role_host.py` is a single-writer file: S1 owns the `status` implementation against the frozen schema; S2 owns consumer/docs and joined verification. If S0 producer semantics change, reconcile contract and fixtures before the join. Do not describe the lane as supported solely because producer and consumer unit tests pass. The join runs actual launch/delivery against a mock and verifies host intent/log → status → ledger classification once, with no API-pool entry or native double-count. Re-read after the S1 crash cuts and persistence failures: discover intents independently of successful launch rows, expose uncertainty about possible charges when evidence is incomplete, exercise orphan cleanup, and prove no launch/send across a failed pre-effect write. The old Anthropic and Codex tests remain regression gates. Use a disposable workspace/state root and an installed launcher outside the writable workspace.

## S3 — Optional, separately authorized live qualification

**Deliverable:** A single bounded live smoke on the pinned Haiku route, or a concrete hold if not separately approved or if its prerequisites fail. Requires accepted offline join, current confirmation that this specific SDK/subscription route is permitted for the account, an owner-selected non-overage subscription, explicit live approval, and a scoped stop/cleanup owner. Propose one launch and one delivery, at most two requests per turn (four total, no retries), no API credential or fallback, synthetic task/workspace, and no proprietary context. Compare host and provider evidence of exact model, terminal usage and allowed/overage-rejected headers; verify one tool effect, delivery on the same session, credential-marker absence and cleanup. Stop at the first billing/model/protocol uncertainty and do not rerun without a new decision. Record the distinction between live route evidence, subscription quota (unmeasured) and implementation acceptance. No automatically enabled default or claim for other models.

The timer starts at implementation admission with target Pi/Docker, the candidate runtime bundle, disposable state, and builder/reviewer capacity ready. Include build, local gates, root coordination, Astra review, bounded repair/recheck and closure.
