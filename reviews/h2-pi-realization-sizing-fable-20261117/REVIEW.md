### Findings

**P1-1 — Missed store coupling: `settle_native_turn` already fences every Pi protocol/profile digest out of native settlement.**
`lifecycle-store/src/native.rs:3021-3037` refuses settlement when the session's `protocol_digest` or `profile_digest` equals any of `pi_settlement::pi_protocol_digest()`, `pi_coding_*`, or `pi_analysis_{protocol,profile}_digest()`. Placement A ("store unchanged"; session "binds a Pi Host protocol digest", §2 A; L2) only holds if L2 mints a digest *outside* that fenced set. The document does not mention the fence, so (a) the "no change in `lifecycle-store`" claim is conditional and unstated, and (b) the store owner's question in §6 ("confirm no store change is needed") omits the one place where that owner has already drawn a Pi-versus-native boundary. This also bears on §3 fairness to alternative B: the existing fence is evidence the store owner intends Pi grammars to be distinct, which weighs toward B (or at least toward an explicit owner decision) rather than "A is the simpler architecture".
*Correction:* add to §1/§3 that `settle_native_turn` (`native.rs:3021-3037`) refuses the store's known Pi digests, that L2's new identity must not collide with them, and rephrase the store-owner question as: "accept a Pi Host identity that passes the native grammar past the existing Pi-digest fence, or require B".

**P1-2 — H3's calls-bundle shape would be refused by the unchanged store and verifier.**
H3 specifies a bundle of "`call_id` → request, attempt, `response_id`, name, arguments". The unchanged consumers require different keys: `retain_native_causal` compares `c["namespace"]`, `c["tool"]`, `c["arguments"]`, `c["call_id"]` against the ingress (`native_causal.rs:98-104`); `verify_delivery` requires `call["namespace"]=="task"`, `call["tool"]=="result_publish"`, `call["inference_call_id"]` (string) and `call["physical_send"]` (u64) (`research_delivery.rs:453-482`). The Codex bundle struct is `CausalCall { call_id, inference_call_id, physical_send, response_id, …, namespace, tool, arguments }` (`lifecycle-codex/src/causal.rs:22-34`). Likewise, the relayed `item/tool/call` frame must carry `threadId`, `turnId`, `callId`, `tool`, `arguments` and a `namespace` of `workspace`/`task` — the actor classifies a call without those namespaces as `unsupported` → `ClaimConflict` (`actor.rs:1823-1852`), and `verify_delivery` checks `params.threadId/turnId` against the input record (`research_delivery.rs:472-474`). H2 says "flat names; Pi sends no `namespace`" but never states that the Host must *add* the namespace on the lifecycle side.
*Correction:* in H2/H3 state that the Host synthesizes `namespace` (`workspace`|`task`) for `item/tool/call`, `dynamicToolCall` items and the bundle; name the bundle keys as `call_id`, `inference_call_id`, `physical_send`, `namespace`, `tool`, `arguments` (`response_id` optional — only echoed at `research_delivery.rs:634`).

**P2-1 — Settlement's `thread/read` and item-shape requirements are under-specified in H1.**
Beyond "`thread/read` from the Host's own record", `settle_native_turn` requires: the history row be a qualified Response (`method IS NULL`) at the cited transport/sequence (`native.rs:3351-3353`); `result.thread.id` match and `historyMode == "legacy"` (:3357); exactly one matching turn with `status == "completed"` and `itemsView == "full"` (:3362-3368); ≤1024 items; each `dynamicToolCall` item (both `item/completed` and history) with `status:"completed"`, `success:true`, matching `arguments` and `contentItems` equal to the actor's returned result (:3137-3160, 3185-3212, 3398-3420); every completed `agentMessage` equal to its history counterpart except `id` (:3436-3451); exactly one completed `agentMessage` whose text equals the final text (:3454). Eligibility of the terminal additionally requires `params.turn.error` to be **present and null** (`native_input.rs:158-164` uses `.get("error") != Some(&Null)`), not merely absent. None of these change the estimate's order of magnitude, but H1's 600–900 lines is predicated on an unstated subset.
*Correction:* list the required `thread/read` result shape and the explicit `"error": null` in H1.

**P2-2 — Runner harness surface and capture timing missed in L1/H3.**
L1's harness trait list omits `captures_native_input`/`acquire_native_input` (`operations/mod.rs:264-283`, :797-809), `observe_protected_surface` (:507), `send_notification` (:436), `pid`, and the lease methods. Two behaviours matter for the Host: (a) the runner acquires input immediately on the terminal frame, *before* `thread/read` and before checking status (:797-813), so the Host's H3 artifact must be complete when it emits `turn/completed`; (b) on adverse terminals (`turn/failed`, `turn/interrupted`, `error` with `willRetry:false`, or `turn/completed` with non-completed status) the runner also acquires and retains input (:264-283), so H3 must produce an (ineligible) artifact for failed turns, not only completed ones. Also, `code_mode_host` is a `NativeLaunch` flag that drives `verify_code_mode_host(&config.executable, CODE_MODE_HOST_SHA256)` (:871-877), `ExpectedToolSet::from_dynamic_tools(.., code_mode_host)` (`tool_registry.rs:115-153`) and `validate_effective_policy` (:1275); L1/L2 should say the Pi realization runs with it off.
*Correction:* extend L1's trait list and add the two timing requirements to H3; no size change beyond noise.

**P2-3 — "No record claims Codex" (§2 A) is not fully true with the store unchanged.**
`retain_native_causal` hard-codes the record scope `"controlled-native-causal-evidence-v1; explicit direct/same-turn-code-mode; historical non-authority evidence"` (`native_causal.rs:105`). A Pi causal record produced under A would carry a code-mode claim. Small, but it contradicts the truthfulness argument that motivates A over B.
*Correction:* either note it as an accepted inaccuracy for the store owner to rule on, or move that one literal into the "touches `lifecycle-store`" column.

**P2-4 — §4 mis-describes the failure mechanism for a Pi request body.**
`snapshot_projection` does not fail on a missing `namespace`; at `research_delivery.rs:248` it `continue`s, so with no namespaced call it returns `Ok(None)` (:349) and `verify_delivery` falls through to `text_projection` (:593-602). The request/card/reconstruction literals then fail the unique-visibility check (:617-626) because they appear JSON-escaped inside the tool-output string. Net outcome (refusal) and T1's remedy are right; the stated stage is not.
*Correction:* "fails `verify_delivery` at the visibility check because `snapshot_projection` skips namespace-less calls (:248)".

**P3-1 — "Preparation fence (`actor.rs:2726`)" is a read-time fence.** Line 2726 is inside `native_causal_read`, the actor op the task host's `acquire` calls; the store also refuses at `native_causal.rs:55-61` and :197-201. The label follows the comparison document but should say "causal-read fence".

**P3-2 — Alternative B's "+800–1 500 lines" and C's dismissal are unenumerated.** B's figure has no item list; C's two reasons (credentials into `lifecycle-service`; blocking loop vs async actor) are sound but the dependency-tree claim is asserted, not shown. Not unfair, but not sized.
