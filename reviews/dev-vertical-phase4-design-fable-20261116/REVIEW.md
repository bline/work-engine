# Independent design review: phase 4 hosted Pi provider transport

Subject: `02f7a571` on `rescue-detached-20260911`. Working-tree blobs for all 14 manifest paths match the commit (checked with `git diff --stat 02f7a571` over the review paths: empty). Read-only; no builds, tests, Docker or network were run.

## Disposition

**Accept with required changes** for proceeding to piece (b). The piece-(a) state machine is sound on the races I could trace, and the operator's specific question resolves as "handled, no defect". The design, however, leaves the financial mapping onto the existing `provider_request` ledger unspecified in exactly the places the two binding requirements bite, and one statement in the design contradicts binding requirement 4. The required changes below are specification changes, not redesign.

## Confirmed defects and required changes

**R1 (P1, design, §3 and decision 2). The existing financial owner has no admissible path for a second attempt.** `coding_provider_frame` keeps one `Reservation` per request id (`pi_coding_provider.rs:253` via `provider_requests: BTreeMap<u64, Reservation>`, insert at `:410-416`). It refuses a new `provider_request` while any reservation is unsettled (`:382-385`), and the only settlement path is `provider_complete` with `http_status == Some(200)` and a raw `response.completed` (`:484-523`). A definitive head refusal (401/402/403/429) therefore ends as `provider_failed = true` (`:488`) and blocks every further grant. Under the design as written, failover is impossible, or the router (`pi_route.rs:199-230`, which *does* release on `Refused`) would admit an attempt the financial owner never reserved for. That is the "two ledgers" the design says it avoids.
*Required change:* specify, before implementation, (a) per-attempt sub-records under each request id (e.g. `Reservation.attempts: Vec<Attempt{attempt, reserved, settled, http_status, raw_terminal, disposition}>`), each durably saved before its upstream dispatch; (b) the single release rule the financial owner applies: an attempt's reservation is released only on `Progress::Refused` (head status in `refusal_status`, zero bytes relayed, body drained to framed end and screened, `pi_stream.rs:676-691`), or when a head-phase cancel is confirmed *before* any upstream bytes were sent; (c) the ordering: financial owner reserves attempt N+1 → `router.next()` → `PiOwner::enter` → dispatch. The router's `allowance_units`/`reserve_units` should be set so it never refuses on allowance (or its allowance check removed), leaving it route order, refusal-driven switch and provenance only, as §3 intends.

**R2 (P1, design, §3 and `pi_pilot.rs:574-589`). Per-attempt effect identity is not expressible with the current key.** `Effect::Provider(u64)` keys `pi_effect` rows as `provider:{n}` (`:585`) and `enter` inserts with `pi_effect_unknown_no_retry` on conflict (`:464-468`). The live Host uses the *request* id (`pi_coding_provider.rs:426`); the probe uses the router's global *attempt* counter (`pi_native_tools_probe.rs:336`). A second attempt for request id 1 keyed `provider:1` would be refused as a replay. The design does not say which key space the hosted profile uses, nor when the lease is `observed`. In the live Host today the lease covers only the IPC grant write and is observed with a constant digest (`pi_docker.rs:665-711`); in the hosted path the effect is the host's own upstream request.
*Required change:* key the effect per attempt (global attempt counter, or a new `Effect::ProviderAttempt(request, attempt)`), hold the lease from before dispatch (as `connect` does at `probe:39`) through the stream, and observe it with the relay digest (`probe:454`) or the refusal digest (`probe:378-380`). This is also what makes "an uncertain attempt can never authorize another" hold at the admission owner, not only in the router.

**R3 (P2, design §4 vs decisions item 4). The design claims the raw-screened-SSE gap is addressed; it is not.** §4 says producing `rawTerminal` from relayed bytes "also addresses the review's raw screened SSE gap". The record README (`:74-76`) and `Relay::evidence()` (`pi_stream.rs:250-266`) show only digest, chunk timings, usage and terminal fields are retained; `forwarded` is dropped after `record_control("stream-NNN")` (`probe:426`). Decision 4 says terminal-event capture satisfies settlement only.
*Required change:* strike the sentence, and either add retention (see focus 3) or obtain the narrowing decision before (c).

**R4 (P2, `pi_stream.rs` API + `probe:308-327`). `response-unavailable` and its cancel crossing live outside `Session`.** The no-attempt answer and the head-phase cancel that can cross it are handled ad hoc in the probe. In the native, `response-unavailable` is a `crossing` frame (`pi-native-tools.mjs:20`) and `release()` keeps reading until `response-cancelled` (`:24-26`). A Host loop that sends `response-unavailable` and moves on leaves the native blocked. The design's "route provider_fetch/pull/cancel/ack for the active request id" does not cover this.
*Required change:* add an `unavailable(code)` entry to `Session` (or a sibling that owns the stream identity) so the Host loop has one deterministic owner for every frame of a stream, including pre-dispatch cancels (see R5).

**R5 (P2, design + `probe:303-343`). A head-phase cancel arriving during admission is not read before dispatch.** Per attempt the probe does `router.next` → `enter` → `check_current` → write the request (`connect`, `probe:40-41`) → only then `relay`, which is the first point where a pending native `cancel(1)` is read. The record's `unavailable4`/`evidence.json:408` shows this: Pi cancelled during ~10 s of admission and the attempt was correctly left uncertain, but a request had been sent and a reservation consumed for nothing. In the Host loop the same frame would arrive via `coding_advance` with no `Session` to route it to.
*Required change:* specify that after admission and before any upstream byte is written the host checks for a crossed `cancel(1)` (`Channel::readable`), confirms it, and treats the attempt as not dispatched (reservation releasable under R1(b)).

## Risks and open questions

**K1 (P2, risk, unverified sizes). Relay bounds versus the financial reservation.** `MAX_RESPONSE = 1 MiB` (`pi_stream.rs:19`, enforced at `:730-732`) ends a stream as `Interrupted("upstream_response_bound")` → uncertain → full reservation retained and the request blocked. The reservation covers 128k output tokens (`docs/pi-coding.md:99-103`). I have not measured SSE bytes per token, so whether a long coding turn can exceed 1 MiB is `not established`; the mismatch between the two bounds is from source. Similarly the probe's 10 s socket read timeout (`probe:36`) would turn a provider pause longer than 10 s into `upstream_interrupted`. For (b) the design should state the upstream read timeout and response bound policy relative to the consumption deadline and the catalog `maxTokens`, rather than inheriting probe constants.

**K2 (P3). `on_native` can block up to `DRAIN` = 1 s.** `(AwaitOp, "cancel")` waits on `reader.data(DRAIN)` when a terminal provider event has been forwarded (`pi_stream.rs:606-619`). It is bounded, but it is a blocking wait inside the event-driven API and in the Host loop it stalls one tick by up to 1 s. Acceptable if documented; otherwise make it a short-lived state polled by `poll()`.

**K3 (P3). Host-produced `rawTerminal` needs a definition.** `provider_complete` requires `raw["eventType"] == "response.completed"`, `raw["status"] == "completed"` and integer token fields (`pi_coding_provider.rs:492-513`). `pi_stream::usage` does not carry `response.status` (`:330-341`). Specify that the host emits the full data payload of the last `response.completed` event in `forwarded` (mirroring `rawTerminalEvidence`, `pi-native-access.mjs:19-23`), `backendModel` from `response.model`, and `httpStatus` from `Relay.status`; and that in the hosted profile the container no longer emits `provider_observation`, or the host refuses "duplicate provider HTTP response" (`:452-455`).

**K4 (P3, `pi-native-tools.mjs:38`). Unexpected body frame settles without a cancel handshake.** The `else{settle();throw}` branch in `pull` marks the handle done, so the next `send()` will not release it, and the host stays in `AwaitOp` until a foreign frame yields `stream_interleaved_frame`. Deterministic (attempt uncertain) but a `release()` there would close cleanly.

**K5 (open). Request body re-send on failover.** A failover re-sends the identical body to a different route/payer. For 401/402/403/429 at the head nothing was processed, so no duplicate coding effect; tools only run after a `done` event, which requires a relayed stream. This holds as long as `refusal_status` stays limited to pre-processing statuses; do not add 5xx to it.

## Focus areas

**1. Financial correctness.** Duplicate coding or tool effects cannot arise from the stream mechanism: a switch happens only on `Progress::Refused`, where nothing reached the consumer and the fetch is still awaiting a head (`pi_stream.rs:447-456`); tools run after `done`. Per-attempt identity and reservation are *not* yet provided by the existing owner (R1, R2). No release without authorization: today the owner never releases at all, which is safe but forbids failover; the release rule must be written (R1(b)). An uncertain attempt cannot authorize another: enforced in the router (`route.rs:141-147`) and in the owner's unsettled check (`provider.rs:382-385`), and both must stay. Suggested mapping: `provider_request(id)` → reserve attempt 1 under id → grant to the container once (the container is attempt-blind) → host dispatches attempt k → `Refused` releases attempt k and reserves attempt k+1 (if the router permits) → relayed stream produces host `provider_observation` for the attempt that reached the consumer → container `provider_complete(id)` settles that attempt only. Underspecified today: the attempt record shape, the release rule, the effect key, lease span, and which side emits `provider_observation`.

**2. Host-loop integration.** Stream progress cannot block the loop if `poll` is called with a zero or small wait: the reader thread owns all upstream blocking (`pi_stream.rs:360-424`), `on_native(pull)` advances with `Duration::ZERO` (`:604`), and `abort` is a non-blocking shutdown. Exception: K2. Cancellation races: head phase `(Head|Refusal, cancel)` → confirmed and upstream closed (`:591-598`), with a crossing head discarded by the native's `crossing` list; overtaking a pull `(Upstream, cancel)` → confirmed, pull answered by the confirmation (`:625-633`), native `pull` returns on `cancelling` before the ordinal check (`:34`); crossing a terminal `(Close, cancel)` → confirmed, `closing = cancel-after-terminal` (`:638-642`); crossing `response-unavailable` is deterministic only because the probe hand-codes it (R4). A cancel crossing a *refusal* downgrades a definitive refusal to `Cancelled` (conservative; fine). Interleaving: any non-stream frame while a stream is open is `stream_interleaved_frame` (`:644`); the native enforces release-before-next-envelope (`:67-70`). The integration must map that error to "attempt uncertain, reservation retained" and must not let `coding_advance` treat it as a bare protocol error that kills the job without recording the attempt.

**3. Evidence completeness.** Not provided (R3). Minimal mechanism: retain `Relay.forwarded` (already the *screened* bytes) per attempt as a store artifact under the existing retention path, bound by the `forwardedSha256` already in the control record; refusal bodies from `Progress::Refused` likewise. Capacity from source: `MAX_RESPONSE` 1 MiB per stream, store `MAX_STORE` 16 MiB with `MAX_STORE - 3*MAX_SNAPSHOT` = 10 MiB for non-closure retention (`pi.rs:22-23, 771-775`), six requests max (`docs/pi-coding.md:103`): 6 MiB worst case fits, with no headroom for failover attempts that relayed bytes (those are uncertain and end the job anyway). If the acceptance owner narrows instead, the narrowing must say that only digest, chunk timing, normalized usage and the terminal event are evidence, and that per-byte replay is not reconstructible.

**4. Admission latency.** From source, one `PiOwner::enter` performs `ingest_control` (one `control::head`, which runs the board dump, `scoped_pilot.rs:167-170`), then `action` → `begin_current` → `current()` and then a second `begin_current` → `current()` (`pi_pilot.rs:443-472`). Each `current()` runs `inspect::collect` (board dump + `usage_ledger.py control`, `inspect.rs:123-124, 197-206`) and `control::head` (board dump again) = 3 subprocess runs. `check_current` and `consumption_deadline_millis` each re-run `current()` via `open_unchecked` (`:636-660`), 3 more each. Counting the live Host path per attempt (`provider.rs:426-434`): 7 + 3 + 3 = 13 pinned-Python subprocess spawns, each bounded at 10 s (`source.rs:62-64`), and each `run_bounded_fenced` re-hashes the interpreter, script and every dependency pin twice (`source.rs:102-106, 178-181`, `pinned` reads and SHA-256s files up to 128 MiB). The 30 s budget freshness rule (`pi_pilot.rs:343`, `:621`) prevents caching across checks by design. Per-spawn timing is unverified; the structure alone explains seconds per attempt. Raising Pi's head timeout to 60 s treats the symptom and is defensible as a stop-gap, but it also delays detection of a genuinely stalled provider head from 10 s to 60 s and relies on the container's clock rather than the host's. The right fixes are in the admission owner (one `current()` per `enter`, pass the evidence from `begin_current` into the lease instead of re-collecting, cache the board dump within a single call), plus R5 so an in-flight cancel is honoured before dispatch. Those are a separate owner's change; the design should name them as a dependency, not absorb them.

## Operator's specific question

**Handled; no defect confirmed.** After the head, `openResponse` removes its `abort` listener (`pi-native-tools.mjs:46`). Three facts make this safe:

1. The fetch `signal` is Pi's *combined* controller signal (`openai-codex-responses.js:267-268`), and `combinedSignal.cleanup()` runs in the `finally` of the fetch await (`:283`), detaching it from Pi's abort signal and the header timer. The receiver always sets `timeoutMs` (`pi-native-tools.mjs:103`), so two signals are combined and the fetch signal can never fire after the head regardless of the listener.
2. Body-phase aborts travel through `parseSSE(response, options.signal)` (`:584-593`): `onAbort → reader.cancel()`, and the `finally` also calls `reader.cancel()` (`:636-638`). Per the Streams spec, cancelling a readable stream invokes the underlying `cancel()` even with a pull outstanding, which is `openResponse`'s `release()` (`:39`). `release()` sends `cancel(++ordinal)`, awaits the in-flight read, and reads until `response-cancelled` with its ordinal, tolerating crossing chunk/terminal frames (`:21-27`). On the host, `(Upstream, cancel)` and `(AwaitOp, cancel)` both confirm (`pi_stream.rs:606-633`).
3. The idle timer is armed only while a `pull` is outstanding (`:32-33`), and `onIdle → session.abort()` reaches the same `parseSSE` path. Release-before-next-envelope (`:70`) covers an open handle at the next `tool`/`fetch`, and a settled handle short-circuits.

Residual edges, none a defect: an abort between fetch resolution and `parseSSE` listener registration is caught by `parseSSE`'s initial `signal.aborted` check plus its `finally` cancel; an errored stream (`c.error`) does not invoke `cancel()`, but the host has already sent its terminal and received `ack` (`:28-29`); K4 above.
